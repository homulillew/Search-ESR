我们前面其实逐步把方案从“原始 ESR + 一堆约束”收敛成了一个比较清晰的方向。核心要点大致可以压成下面这些。

## 1. 对原始 ESR 的总体判断

ESR 的**核心思想是合理的**，尤其适合长 Search：

* Search result 和真正 Evidence 分离；
* Evidence 要可追溯、不可随意覆盖；
* 长程搜索不能只依赖 chat history，需要显式 Research State；
* 最终答案要有 Evidence grounding；
* Verification 失败不能只返回 wrong，而要指出缺什么；
* 搜索应该围绕未解决问题继续，而不是盲目扩张。

但原始实现的问题是：**模型、system prompt、guidance、hard gate、recovery heuristic 同时控制 workflow**。

于是代码逐渐变成：

```text
模型犯协议错误
→ gate 拒绝
→ guidance 修复
→ 新的 failure
→ 再加 breaker
```

这是典型的 patch stacking。

---

## 2. 我们从 rollout 里归纳出的三个最核心 bad case

### A. 只 Search，不真正读证据

模型容易：

```text
search
search
search
search
```

因为 Search 风险低、反馈快，有“假进展感”。

我们最后倾向于：

> 尽量从接口设计上消灭 `search → open` 的负担。

例如：

```text
search(query)
→ document retrieval
→ within-document chunk retrieval
→ 直接返回 relevant evidence chunks
```

而不是再用复杂状态机强迫模型 open。

---

### B. 重复搜索 / Candidate Lock-in

模型一旦先猜：

```text
candidate = Alice
```

后面很容易从：

```text
找答案
```

变成：

```text
证明 Alice
```

于是：

```text
Alice + clue
Alice + clue 换种说法
Alice + clue 再换种说法
```

这里我们区分了几个问题：

* 结果重复；
* 结果不重复但全是噪声；
* 没找到反证；
* 已经看到反证但没有更新 belief；
* 当前 information need 本身定义错了。

最后我们不希望 Harness 为每一种 failure 各写一个 subsystem，而是用一个更通用的机制：

> **连续几个 research cycle 没有产生语义 State 变化 → REPLAN。**

REPLAN 时由强模型重新判断：

* candidate 是否错了；
* 当前问题是不是问错了；
* query 是否太窄；
* 是否应该换另一个 clue；
* 是否应该重新打开 candidate space。

Harness 只检测“没进展”，不替模型判断“谁对谁错”。

---

### C. 已经够了但不会 Submit

这个我们最后判断得最明确：

> **Submit 不应该是模型 action。**

如果 Final Verification 已经通过：

```text
Harness → DONE
```

直接返回结果。

不要再让模型决定：

```text
我要不要 submit？
```

---

## 3. 我们重新定义了 Harness 和模型的边界

这是整个讨论最重要的一条。

### Harness 负责

```text
Memory
Evidence provenance
Search trace
Compact state
No-progress detection
Budget
Retry
Final verification trigger
Stopping
```

### 模型负责

```text
问题到底在问什么
当前缺什么信息
应该搜什么
Evidence 意味着什么
当前 candidate 是否合理
是否该换假设
如何重新规划
```

一句话：

> **Harness 管 Runtime，模型管 Semantics。**

---

## 4. 对 ReAct 的理解也被修正了

经典 ReAct 更像：

```text
Observation
→ Model 自己决定下一步 action
→ Tool
→ Observation
```

我们讨论的方案不是完全抛弃 ReAct，而是：

> **全局由薄 Harness 提供 memory / progress / checkpoint，局部仍让强模型自由 ReAct。**

也就是：

```text
Global thin harness
+
Local agentic search
```

我们后来明确反对把 Harness 做成：

```text
SEARCH
→ OPEN
→ EXTRACT
→ VERIFY
```

这种 rigid FSM。

---

## 5. “状态切换”这个概念也被重新澄清

Harness 不应该决定：

```text
Alice 错了
Bob 对了
下一步一定搜 X
```

它可以决定的是：

```text
当前研究连续没有进展
→ 需要 REPLAN

当前 candidate 看起来成熟
→ 触发 Final Verify

Final Verify PASS
→ DONE
```

也就是：

> Harness 决定“什么时候需要重新思考/验证/停止”，
> 模型决定“重新思考后的语义结论是什么”。

---

## 6. Gap / Information Need 的讨论最后被简化了

我们一度拆成：

```text
Gap
→ Information Need
→ Query
```

后来觉得太复杂。

v0 可以统一成：

```text
open_questions
```

例如：

```text
Who won X in 2008?
```

它同时表达：

* 当前还缺什么；
* 下一轮 research 的目标是什么。

特别强调：

不要轻易写成：

```text
Find evidence that Alice won X in 2008.
```

因为这会强化 confirmation bias。

更好的形式是：

```text
Who won X in 2008?
```

尽量保持 candidate-independent。

---

## 7. 对复杂 BC+ 初始化的结论

不要：

```text
Question
→ one query
```

也不要：

```text
Question
→ 一开始构建巨大 DAG
```

第一版更合理的是：

```text
Question
→ compact criteria
→ 1~3 个不同的 initial open questions / search directions
→ local research
```

初始化目标不是立刻猜 answer，而是避免第一步 framing 错误把后面全部锁死。

---

## 8. Requirement Graph / Constraint Graph 最后决定暂缓

我们讨论过：

* Requirement；
* Constraint；
* Slot；
* DAG；
* Candidate × Constraint Matrix；
* Lazy Graph。

理论上都有价值。

但最后的判断是：

> **不要因为理论上有帮助，就先全部落地。**

Graph 更适合当未来能力：

* 真实 rollout 如果证明“中间实体依赖”确实是大量失败根因；
* 再加 Lazy Constraint DAG。

而且即使以后加：

> Graph 是 Harness 内部结构，模型只看当前 frontier。

绝不能让模型自己维护图。

---

## 9. 我们对 Progress 的最终理解

最重要的一条：

> **搜到新文档不等于 Research Progress。**

新 doc、不同 query、不同结果只是 retrieval activity。

真正 progress 是：

```text
candidate 改变
发现新的有效事实
open question 被解决
出现新的关键 open question
final readiness 改变
```

所以：

```text
高 novelty + 0 state change
```

一样可能是在搜垃圾。

最后我们决定：

> 不做复杂 Productivity / Drift / Saturation taxonomy。

第一版只看：

```text
Compact ResearchState 连续 N 轮基本没变化
→ REPLAN
```

---

## 10. Evidence 设计的核心保留

我们一直比较坚定：

```text
SearchHit != Evidence
```

而且 V2 更希望 Evidence 最小单位变成：

```text
immutable chunk
```

即：

```text
KnownFact
→ chunk_id
→ document/source
```

这样自然保证：

```text
模型真正看到的内容
=
Verifier 可以使用的内容
```

避免旧 ESR 那种“整篇 Evidence + 后续重新构造 chunk view”的复杂度。

---

## 11. Verifier 最后的定位

我们最后的结论不是“删除 verifier”，而是：

> **保留 Verification 能力，但不再作为 model-facing tool。**

不再：

```text
Model → verify_answer()
```

而是：

```text
Harness 在 checkpoint 自动启动 independent verifier
```

尤其 Final Verifier 建议保留。

它只做 skeptical audit：

* candidate 是否满足原始问题；
* 关键事实有没有 citation；
* evidence 是否真的支持 claim；
* 是否还有关键 missing issue；
* 是否存在 contradiction。

如果：

```text
PASS
→ DONE
```

如果：

```text
REPAIR
→ missing issue 加回 open_questions
```

---

## 12. Verifier 的错误类型必须拆开

旧 ESR 一个严重问题：

```text
JSON parse error
→ needs_revision
→ semantic gap
→ 模型乱搜
```

V2 必须区分：

```text
semantic repair
format error
infra error
context error
```

其中：

```text
format / infra
```

Harness 自己 retry。

不能污染 Research State。

---

## 13. 我们最后收缩出来的最小 State

最小 v0 大概只需要：

```json
{
  "question": "...",
  "criteria": ["..."],
  "candidate": "...",
  "known_facts": [
    {
      "fact": "...",
      "citations": ["chunk_x"]
    }
  ],
  "open_questions": ["..."]
}
```

不用：

```text
完整 DAG
Hypothesis lifecycle
InformationNeed object
ProgressEvent object
ConstraintEvaluation matrix
```

这些先不做。

---

## 14. 最终 Harness 只保留三个核心通用机制

这是我们最后最重要的收敛。

### 机制 1：Search 直接产生可用 Evidence

解决：

```text
只 Search 不 Open
```

---

### 机制 2：Compact State + No-progress → REPLAN

统一解决：

```text
重复 query
不同噪声 query
candidate lock-in
错误 search direction
错误 open question
```

---

### 机制 3：Final Verify → Auto Stop

解决：

```text
不会 submit
过早 submit
答案看似合理但 grounding 不足
```

---

# 15. 最终我们想做的东西

不是：

> 一个更复杂、更严格的 ESR Agent。

不是：

> 一个模拟完整人类 Research cognition 的系统。

而是：

# Thin Research Harness

核心就是：

```text
Compact Memory
+
Grounded Evidence
+
No-progress → Replan
+
Final Verify → Auto Stop
```

强模型仍然拥有主要 Research intelligence。

---

## 一句话总结整个讨论

我们最开始想：

> “怎么用更多 State / Gap / Gate 教模型走正确流程？”

后来逐渐变成：

> **“哪些流程问题根本不值得让模型承担，哪些语义判断必须留给强模型？”**

最终答案是：

> **Harness 越薄越好，只外置模型在长 Search 中最稳定的短板：记忆、证据追踪、无进展检测和停止；其他研究行为尽量交给强模型。**
