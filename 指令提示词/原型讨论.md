# 一、项目背景

原 ESR Harness 的核心思想是：

```text
Search
→ Evidence
→ TaskState
→ Verify
→ Gap
→ Search / Repair
→ Submit
```

它相比普通 Search Agent 的正确点包括：

1. Search result 与真正 Evidence 分离；
2. Evidence 不可变并可追溯；
3. 长程 Search 不完全依赖 conversation history，而有显式 Research State；
4. 答案在提交前需要经过 Verification；
5. Verification 失败时返回 Gap，而不是简单 wrong；
6. Agent 与 Verifier 尽量基于同一份实际可见 Evidence；
7. 整条 trajectory 可审计。

这些思想仍然有价值。

但当前实现是在“模型自己管理整个 Agent workflow”的前提下逐步打补丁形成的，已经出现明显复杂度膨胀。

当前代码存在：

```text
Prompt policy
+
Model policy
+
next_step_guidance
+
hard legality gate
+
recovery heuristics
```

多层同时控制同一个 workflow 的情况。

典型函数包括：

```text
_search_open_break
_illegal_read_break
_stale_evidence_id_break
_gap_worklist
_verify_service_glitch
_soft_deadline_note
```

这些不是单独的代码质量问题，而反映旧架构本身存在责任边界不清的问题。

# 二、实际 Rollout 中最重要的 Bad Cases

我们实际在 BrowseComp-Plus 长程 rollout 中反复遇到以下问题。

这些问题在更换 prompt、方案或模型后仍然会出现，因此不能继续主要依赖 prompt engineering 解决。

---

## Bad Case 1：模型只 Search，不 Open / 不真正读证据

表现：

```text
search
search
search
search
...
```

或者虽然 search 返回很多结果，但模型不去 inspect 真正正文。

根因不是简单“模型不知道工具”。

Search 对模型来说：

* 成本低；
* 每次立即返回大量新 token；
* 有虚假的进展感；
* 不需要对某个结果作 commitment。

而 Open / Inspect 要求模型做选择。

旧 ESR 用：

```text
连续 search N 次 → 强制 open top1
```

这类规则纠偏。

但这属于事后补丁。

新的设计应优先考虑：

**不要让 Search 和 Evidence Acquisition 之间存在不必要的 workflow burden。**

例如：

```text
search(query)
```

可以直接返回：

```text
top documents
+
每个文档与 query 最相关的少量 evidence chunks
```

即：

```text
Search
→ document retrieval
→ within-document chunk retrieval
→ actual evidence
```

这样从结构上消除：

```text
search 了但永远不 open
```

这个 bad case。

如果仍保留 open/read，也应避免让模型承担大量 ID 和记账责任。

---

## Bad Case 2：重复类似 Query / Candidate Lock-in

典型轨迹：

```text
先猜 Alice
↓
search Alice + condition
↓
证据不足
↓
换个类似 query 继续搜 Alice
↓
结果类似或全是噪声
↓
仍然围绕 Alice 搜
```

这里实际有多个不同 failure：

### A. Retrieval repetition

query 不同，但返回同一批文档。

### B. Retrieval drift

每次返回不同文档，但都是噪声。

所以：

```text
高 novelty != 有 progress
```

### C. Hypothesis fixation

真正严重的是：

模型从：

```text
answer discovery
```

滑向：

```text
answer justification
```

一旦把 Alice 当成 answer，后续搜索目标变成：

```text
如何证明 Alice
```

而不是：

```text
谁真正满足条件
```

即使当前 candidate 是错的，也很难恢复。

### D. Belief update failure

还要区分：

```text
没找到能推翻 Alice 的信息
```

和：

```text
已经看到了推翻 Alice 的信息，但仍不改变 hypothesis
```

这是两个不同问题。

---

## Bad Case 3：已经信息充分，但模型不会提交

表现：

```text
已有 candidate
Evidence 足够
甚至 verify 已通过

但模型继续 search
```

这不是值得训练模型学习的能力。

因为：

```text
Search 是可逆动作
Submit 是不可逆 commitment
```

模型天然倾向继续搜索。

所以：

**最终 Submit 不应该继续是一个 Model-facing Action。**

一旦 Harness 判断 Final Verification PASS：

```text
Harness → DONE
```

自动返回答案。

不要再问模型：

```text
你要不要 submit？
```

---

## Bad Case 4：Gap 未必真正驱动下一轮 Search

旧 ESR：

```text
Verifier
→ free-text Gap
→ 放回 Prompt
→ Model 自己 search
```

问题：

Gap 只是：

```text
哪里没证明
```

并不天然意味着：

```text
下一步应该搜索什么
```

而且 Candidate-conditioned Gap 很容易进一步强化错误 Candidate：

```text
缺少证明 Alice 满足 R3 的证据
↓
Alice R3
Alice R3 wording2
Alice R3 wording3
```

所以需要明确：

```text
Gap / Missing Issue
```

应该表达成：

**下一步真正需要知道的语义问题。**

但不要为了这一点再创建庞大的 Gap / InformationNeed / Query 多层对象体系。

v0 可以简单合并成：

```text
open_questions
```

例如：

```text
Who won X in 2008?
```

而不是：

```text
Find evidence that Alice won X in 2008.
```

尽量让 open question 保持 candidate-independent，避免 confirmation search。

---

## Bad Case 5：复杂 BC+ 问题一开始就容易跑偏

BC+ 原始问题往往：

* 条件多；
* 多跳；
* 一个 clue 对应中间实体；
* 直接把所有约束塞进 query 往往 recall 很差；
* 一开始错误 framing 后，整个 trajectory 会围绕错误方向滚雪球。

所以不能简单：

```text
Question
→ one initial query
```

但也不要一开始构建复杂 Constraint Graph。

新的第一版应该：

```text
Question
→ compact plan / criteria
→ 1~3 个语义上不同的 initial open questions
→ local research
```

初始化的目标不是马上猜最终答案，而是：

```text
形成少量 plausible search directions / candidate space
```

避免 premature commitment。

# 三、从 Bad Cases 得出的核心思想

新的 Harness 不应该继续发展成：

```text
更严格的 ReAct Agent
```

也不应该成为：

```text
复杂 workflow engine
```

而应该是：

# Thin Research Harness

它只负责补模型长期 Search 中最稳定的几个短板：

```text
Memory
Loop / No-progress Detection
Grounding / Provenance
Final Verification
Stopping
```

模型仍然负责主要语义智能。

---

# 四、最核心的架构原则

请整个迁移过程始终遵守下面这些原则。

---

## 原则 1：Harness 管 Research Runtime，模型管 Semantics

模型负责：

```text
问题到底在问什么
当前缺什么信息
该搜索什么
Evidence 说明什么
当前 Candidate 是否合理
是否应该改变假设
如何重新规划搜索方向
```

Harness 负责：

```text
已经搜过什么
已经看到什么
证据来自哪里
当前 compact state 是什么
最近 Research 有没有产生语义变化
什么时候触发 replan
什么时候触发 final verification
什么时候结束
API retry / format repair / budget
```

---

## 原则 2：Harness 不替模型做语义判断

Harness 可以判断：

```text
最近 3 个 research cycle state 没变化
```

但不能判断：

```text
Alice 一定错了
Bob 一定对
```

Harness 可以触发：

```text
REPLAN
```

但 Replan 的语义结果由模型决定。

---

## 原则 3：不要规定唯一正确 Research Trajectory

不要实现：

```text
Search
必须 Open
必须 Extract
必须 Verify
必须 ...
```

这样的固定 DAG。

强 API 在局部 research 内仍然应该保留 agentic / ReAct 能力。

更合理的是：

```text
Harness:
维护 compact state + progress signals

Model:
在当前 research objective 内自由 search/reason
```

即：

```text
Global thin harness
+
Local model autonomy
```

---

## 原则 4：凡是 Harness 已经知道的信息，不让模型重复输出

不要再让模型维护：

```text
action_id
search_action_id
evidence_id lifecycle
coverage bookkeeping
verification_status
submit action
API retry
```

这些是 Runtime metadata。

模型只应该输出：

```text
Semantic Delta
```

例如：

```text
candidate changed
new known fact
open question resolved
new open question
final candidate
```

---

## 原则 5：不要把每个 Bad Case 变成一个 subsystem

禁止类似：

```text
重复搜索 → 新增 RepetitionManager
噪声搜索 → 新增 DriftManager
候选锁死 → 新增 HypothesisLifecycle
Gap → 新增 InformationNeedPlanner
...
```

优先寻找一个通用机制覆盖多个 failure。

当前最重要的通用机制是：

```text
NO_PROGRESS → REPLAN
```

---

# 五、V2 v0 应该非常薄

不要一开始实现：

```text
RequirementGraph
LazyDAG
Slots
HypothesisMatrix
ConstraintEvaluation
InformationNeed
ProgressEvent
SearchProductivityState
...
```

这些概念可以用于分析，但不应该直接全部进入 runtime。

只有真实 rollout 证明必要时才逐步增加。

# 六、建议的最小 Research State

第一版推荐：

```json
{
  "question": "...",

  "criteria": [
    "...",
    "..."
  ],

  "candidate": "...",

  "known_facts": [
    {
      "fact": "...",
      "citations": ["chunk_x"]
    }
  ],

  "open_questions": [
    "..."
  ]
}
```

含义：

### `criteria`

复杂问题的稳定约束。

不要求完整 DAG。

简单题甚至可以为空。

### `candidate`

当前最优 hypothesis。

它必须被明确视为：

```text
tentative / revocable
```

不是 immutable answer。

如果模型重新规划，可以直接替换。

未来如果真实实验表明多 candidate 很重要，再升级成 candidate set。

### `known_facts`

压缩后的真正有价值事实。

必须有 citation。

### `open_questions`

当前真正还需要解决的语义问题。

同时承担：

```text
Gap
Information Need
```

不要再拆得更细。

---

# 七、Evidence 仍然是第一等公民

旧 ESR 中下面这些思想必须保留：

```text
SearchHit != Evidence
```

但 V2 可以进一步简化。

最小 Evidence 单位应尽量是：

```text
immutable chunk
```

而不是整个 document。

例如：

```json
{
  "chunk_id": "c17",
  "document_id": "d4",
  "source": {
    "title": "...",
    "url": "..."
  },
  "text": "...",
  "content_hash": "..."
}
```

后续所有 citation：

```text
fact → chunk_id
```

这样天然保证：

```text
模型真正看到什么
=
Verifier 验证什么
```

避免旧 ESR：

```text
Evidence ID
→ 根据历史 search query 动态重建 chunk view
```

这种复杂机制。

---

# 八、Search API 建议

优先考虑把：

```text
search
open_page
```

两步合并。

例如：

```python
search(query)
```

直接返回：

```text
top N documents
+
每篇 top K relevant chunks
```

模型每次 Search 就真正获得 Evidence。

这样直接根治：

```text
Search 不 Open
```

如果需要后续深挖文档，可以单独提供：

```python
read_more(document_ref, focus)
```

但它应该是可选能力，不是主流程强制阶段。

---

# 九、Search Trace 只用于 Runtime，不要进入复杂 Research Schema

Harness 内部保存：

```text
query
returned doc ids
returned chunk ids
timestamp
```

主要用途：

```text
exact duplicate query suppression
debug
budget
```

可以计算简单结果重合度，但不要因此建立复杂 Search State Machine。

---

# 十、Progress：只保留一个统一概念

核心问题不是：

```text
有没有搜到新文档？
```

而是：

```text
Research State 有没有发生语义变化？
```

例如算 progress 的事件：

```text
candidate changed
new useful fact
open question resolved
new important open question
final answer readiness changed
```

下面这些不算 Research Progress：

```text
又 search 了一次
搜到 5 个新 doc
又打开一个页面
query wording changed
```

---

# 十一、统一处理“重复搜索”和“不同噪声搜索”

不要单独设计：

```text
stagnation
drift
saturation
productivity manager
```

统一看：

```text
最近 N 个 research cycle
compact ResearchState 是否持续没有变化
```

如果连续无变化：

```text
NO_PROGRESS
```

触发：

```text
REPLAN
```

无论底层是：

```text
结果重复
结果不重复但都是噪声
query drift
candidate fixation
open question 定义错误
retrieval strategy 错
```

都交给强模型做语义诊断。

---

# 十二、REPLAN 是唯一建议保留的高级控制操作

REPLAN 不是 tool call，而是 Harness 触发的一次独立语义调用。

输入应是高度压缩的状态，例如：

```text
Original question:
...

Current candidate:
Alice

Known facts:
...

Open questions:
...

Recent research:
- 3 searches
- 0 new useful facts
- candidate unchanged
- open questions unchanged

Task:
Research has not made semantic progress.
Reassess the current approach.

Consider:
- Is the current candidate wrong?
- Is the open question formulated incorrectly?
- Should the search use another clue or anchor?
- Should the current candidate be abandoned?
- Is the current search direction too narrow?
```

强模型输出新的：

```text
candidate
known facts adjustments
open questions
next search direction
```

Harness 自己更新 compact state。

---

# 十三、不要重新实现 Hypothesis Graph

我们之前讨论过：

```text
Requirement Graph
Constraint DAG
Slots
Candidate Matrix
```

这些概念对于分析 BC+ 多跳问题是有价值的。

但 v0 不实现。

只有当实际大量 rollout 表明：

```text
criteria list 无法表达中间实体依赖
```

再考虑 Lazy Constraint DAG。

而且即使以后加入：

```text
Graph 是 Harness 内部结构
模型只看到 Frontier
```

绝不能让模型持续维护 Graph。

---

# 十四、Verifier 仍然保留，但改成 Harness 内部 Checkpoint

不要再保留 model-facing：

```text
verify_answer()
```

Harness 自动决定何时触发 Final Verification。

至少触发条件：

```text
模型认为 candidate 已经成熟
open_questions 为空或只剩非关键项
或者 budget 进入 final checkpoint
```

Verifier 独立新 context。

可以复用同一个强 API，但：

```text
Research Context
和
Verification Context
```

必须隔离。

---

# 十五、Final Verifier 的职责

不是重新解决问题。

只做 skeptical audit：

```text
当前 candidate 是否满足原始问题？
关键 criteria 是否有证据？
known facts 的 citation 是否支持对应 claim？
有没有明显 contradiction？
是否还存在真正关键的 missing issue？
```

输出简单结构：

```json
{
  "status": "pass | repair",

  "missing_issues": [
    "..."
  ],

  "contradictions": [
    "..."
  ]
}
```

不要返回 query。

如果：

```text
repair
```

Harness 将 missing issue 加回：

```text
open_questions
```

然后继续 research。

---

# 十六、Verifier 错误必须与语义失败分开

旧 ESR 一个严重问题：

```text
verifier JSON parse error
→ needs_revision
→ semantic gap
→ 模型继续错误 Search
```

V2 禁止这样。

明确区分：

```text
SEMANTIC_REPAIR
FORMAT_ERROR
INFRA_ERROR
CONTEXT_ERROR
```

其中：

```text
FORMAT_ERROR
INFRA_ERROR
```

由 Harness 内部 retry。

不能污染 Research State。

---

# 十七、Submit Action 删除

旧 ESR：

```text
verify supported
→ 模型 submit_answer()
```

V2：

```text
Final Verifier PASS
→ Harness DONE
```

自动返回答案。

彻底解决：

```text
模型不会 submit
```

---

# 十八、Context Strategy

不要继续把完整 30~100 轮 conversation history 作为主要 state。

每个 research cycle 给模型的核心上下文应是：

```text
Original question
Compact ResearchState
Current open questions
Relevant evidence chunks
最近非常少量 local context
```

而不是全部工具历史。

Search trace / old pages 放在 Runtime Store。

需要时再 retrieval / read_more。

---

# 十九、强 API 的本地自由度

不要把 V2 变成 rigid FSM。

在一次 local research cycle 内，强模型可以自由：

```text
search
reason
search
read_more
reason
```

Harness 不需要规定每一步。

Harness 只在 cycle 结束时收取：

```text
updated compact state
```

并检测：

```text
有没有 semantic progress
是否需要 replan
是否应该 final verify
```

# 二十一、旧 ESR 为什么不继续沿用

请明确认识旧 ESR 的几个结构问题。

### 1. Workflow ownership 不清

同时存在：

```text
System Prompt
Model policy
next_step_guidance
hard gate
recovery rules
```

### 2. 模型承担过多 bookkeeping

例如：

```text
evidence_id
search_action_id
evidence_directory coverage
supporting_evidence
update_state
verify
submit
```

### 3. 每解决一个 failure 又新增一个 recovery

最终形成补丁叠加。

### 4. Evidence Archive 与 Working State 混在一起

所有 open 过的 Evidence 都被要求进入 directory。

长 trajectory state tax 很高。

### 5. visible_evidence gate 产生 stale-id 等次生问题

然后又需要新的 breaker 修复。

### 6. Verifier semantic failure 与 infra/parse failure 混淆

会制造错误 Gap。

### 7. Submit 仍依赖模型主动执行

产生 stop-and-commit failure。

### 8. Prompt / tool schema / runtime 已经出现 contract drift

例如：

```text
read_evidence offset
```

实现已删除但 schema 仍存在。

### 9. `action_budget` / `max_turns` 等概念不统一

### 10. 当前 Harness 已经开始替小模型进行大量 workflow scaffolding

但本次目标已经变成：

```text
强 API + pure harness
```

因此可以大幅收缩。

```text
research_loop.py
verifier.py
runtime.py
```

不要过度拆分。

---

# 二十三、建议的数据对象

只实现必要对象。

例如：

```python
ResearchState
KnownFact
EvidenceChunk
SearchTrace
VerificationReport
```

推荐：

```python
@dataclass
class ResearchState:
    question: str
    criteria: list[str]
    candidate: str | None
    known_facts: list[KnownFact]
    open_questions: list[str]
```

例如：

```python
@dataclass
class KnownFact:
    text: str
    citations: list[str]
```

Evidence：

```python
@dataclass(frozen=True)
class EvidenceChunk:
    chunk_id: str
    document_id: str
    text: str
    title: str
    url: str
    content_hash: str
```

避免一开始创建几十个 enum 和状态对象。

---

# 二十四、Persistent State 与 Derived Runtime Signal 分离

Persistent State：

```text
candidate
known_facts
open_questions
criteria
```

Derived signal：

```text
no_progress_count
recent_search_overlap
budget_remaining
```

不要把所有分析 metric 持久化进 Research State。

---

# 二十五、Progress 检测第一版保持简单

不要先实现语义复杂评分模型。

可以：

1. 每次 local research cycle 前保存 canonicalized state；
2. cycle 后保存新 state；
3. 判断是否有以下变化：

```text
candidate
known_facts
open_questions
```

如果连续 N 个 cycle 基本没有变化：

```text
trigger REPLAN
```

必要时再增加 semantic similarity。

第一版不必设计复杂 reward/score。

---

# 二十六、Search 第一版要求

优先做：

```text
search(query)
→ top documents + relevant chunks
```

要求：

* exact duplicate query 去重；
* document/chunk provenance；
* chunk immutable；
* result caching；
* 不允许模型自己生成内部 action id。

如果暂时不能重构 retrieval backend，可以在 V2 adapter 层包装现有：

```text
EchoRetrievalClient.search
+
get_doc_chunks
```

# 二十七、Backward Compatibility

旧 ESR 可以保留用于历史实验复现。

不要为了 V2 强行修改旧实验语义。

新 V2 应允许：

```text
old ESR
new Thin Harness
```

并存一段时间。

但新 forward benchmark 应使用 V2。

---

# 二十八、测试重点

不要只测 happy path。

必须包含下面几个真实 bad case regression。

### Test 1：Search 直接产生 Evidence

确保不再出现：

```text
search 10 次
open 0 次
```

这一类结构性 failure。

### Test 2：重复 Search

连续不同 wording，返回高度相似结果。

确保：

```text
ResearchState 连续无变化
→ REPLAN
```

### Test 3：不同结果但全是噪声

连续 search 返回大量不同 documents，但：

```text
candidate
known_facts
open_questions
```

均不变化。

同样必须：

```text
REPLAN
```

不能把 new_doc_count 当 progress。

### Test 4：Candidate Lock-in

初始 candidate 错误。

之后 Evidence 长期无法解决关键 open question。

REPLAN 必须允许模型：

```text
replace candidate
```

而不是继续围绕旧 candidate search。

### Test 5：Final Verification PASS

Harness 自动 DONE。

不得再要求 model submit。

### Test 6：Verifier Parse / Infra Error

不能写进：

```text
open_questions
```

必须内部 retry / fail as infrastructure.

### Test 7：Citation Grounding

Final verifier 只能使用：

```text
model actually seen evidence chunks
```

# 二十九、迁移时不要做的事情

明确禁止：

1. 不要一上来实现完整 Requirement Graph；
2. 不要实现通用 DAG scheduler；
3. 不要做 Candidate × Constraint Matrix；
4. 不要做复杂 Search Productivity taxonomy；
5. 不要为 repetition / drift / noise 各写一个 Controller；
6. 不要继续扩展 `next_step_guidance`；
7. 不要让模型继续维护 Evidence IDs；
8. 不要让模型决定 Verify；
9. 不要让模型决定 Submit；
10. 不要把训练 token span / credit metadata 搬进 V2；
11. 不要为了“形式完整”创建大量目前没有实际用处的 dataclass。

# 三十二、成功标准

V2 的成功不定义为：

```text
代码更复杂
State 更完整
规则更多
```

成功应该体现在：

### 行为层

* Search 后真正获得可用 Evidence；
* 重复 / 噪声搜索能统一触发 Replan；
* Candidate 可以被撤销；
* Research State 不随历史线性膨胀；
* Verify PASS 后自动结束；
* infra error 不污染 semantic state。

### 架构层

* Harness 明显比旧 ESR 更薄；
* Model-facing protocol 明显更简单；
* runtime bookkeeping 不再暴露给模型；
* 不依赖几十条 special-case guidance；
* 主要 bad case 被少量通用机制覆盖。

### 可观测性

至少记录：

```text
model calls
search calls
replan count
verifier calls
evidence chunks seen
state changes
final status
```

以便后续分析。

# 三十三、最终设计哲学

整个实现必须始终符合以下一句话：

> **Harness 不是替强模型研究，而是给强模型提供最少但关键的外部记忆、证据追溯、无进展检测和停止机制。**

进一步说：

> **不要尝试在 Harness 中模拟完整的人类 Research cognition。**

Harness 应该尽量薄。

真正的 Research intelligence 仍然属于强模型。

最终目标不是：

```text
一个复杂 Research OS
```

而是：

# 一个 Thin、Progress-aware、Evidence-grounded、Auto-stopping 的 Search Harness

其核心只需要：

```text
Compact Memory
+
Grounded Evidence
+
No-progress → Replan
+
Final Verify → Auto Stop
```

如果这四点做好，就已经解决了目前 rollout 中最主要、最普遍的结构性 bad cases。
