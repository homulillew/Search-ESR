# Search–Open 机械修复与性能检查

本轮不调整 BM25 排序，不加入身份识别、gap 或字段精简。只检查结构边界、连续读取和性能。

## 可复现问题与修复

1. **空标题吞入正文。** 旧正则的 `\s*` 可以跨过换行，`title:` 为空时把下一行正文提取成标题。修复为仅允许横向空白，并要求标题值在同一行。测试在旧实现失败、修复后通过。
2. **定位块边缘可能截断阅读单元。** 保留原锚点和排序，新增从全文句子/行边界修复范围的步骤；只有整个修复范围满足预算才采用，不删除原锚点来换取边界。超长单元依然可能截断。
3. **可识别的 Markdown 表头不在窗口内。** 仅对管道表格及明确分隔行做结构识别；当从表头到命中行的连续范围放得下时一起返回。没有跨位置拼接，没有推断列含义。HTML 表格、复杂多行记录不在本轮处理范围。
4. **重复扩展重复计算。** 文档注册时预存排序后的边界数组；每工具实例以 256 项 LRU 缓存 token 计数。原文和引用不被淘汰，避免破坏后续 Open。

旧实现中三个新增用例失败：一个是真实标题解析回归，两个是新增结构修复能力尚不存在。修复后 11 项针对性测试通过，全量 33 项测试通过。不能将两个新增能力测试的 AttributeError 描述成旧工具执行异常。

## 性能对照

四篇真实文档，每组五次重复 Search 和 around，交替旧新执行顺序。排除 tokenizer 加载，没有模型 API 或召回。表中为单次首次耗时和重复操作中位数，单位秒。

| docid / 字符数 | 首次 Search 旧→新 | 重复 Search 旧→新 | 重复 around 旧→新 |
| --- | --- | --- | --- |
| 67431 / 2,790 | 0.038 → 0.028 | 0.0159 → 0.0042 | 0.0440 → 约 0.0001 |
| 23800 / 29,954 | 0.121 → 0.126 | 0.0161 → 0.0063 | 0.0411 → 约 0.0001 |
| 55516 / 98,580 | 0.308 → 0.242 | 0.0156 → 0.0064 | 0.0379 → 约 0.0001 |
| 54231 / 1,152,951 | 6.161 → 6.332 | 0.0736 → 0.0647 | 0.0189 → 约 0.0001 |

四篇文档的新旧 Search 原文范围一致。重复 around 的结果也满足原文一致、包含旧窗口的要求。性能主要受益于完全相同请求重复时的计数缓存，不能将该加速比例推广到每次都读取新位置的实际轨迹。首次处理没有稳定提速，长 HTML 的全文预处理仍然是主要开销。

最长文档的 documents/windows Python 对象图粗略大小由 5.89 MiB 变为 5.92 MiB。该测量排除 tokenizer、原生内存和计数缓存闭包，不是进程 RSS，也不是内存上限。文档注册表依然随访问文档增长，未在本轮引入可能破坏引用的淘汰策略。

长文档出现 tokenizer 长度警告；此处只做分词计数，不将全文送入 embedding 模型进行前向计算。

## 展开行为与边界

原有 before/after 连续推进、around 保留旧窗口、全文状态、超长文本和 Unicode 检查继续通过。到达边界时仍返回同一不可变窗口与明确状态。本轮没有为了减少返回量改变该契约，也没有修改后续 research state 的上下文组织。

## 当前判断

本轮可以保留确定的机械修复与有界计数缓存，后续新轨迹版本为 v002_raw_windows_mechanical。仍需注意全文预处理与长批次内存增长；暂不据此启动新的语义规则或长链路优化。
