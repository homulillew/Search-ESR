# Query初始化节点设计与实验方案

状态：设计稿 v0.1。本文规定下一轮实现与实验，尚未实现初始化运行时，也没有产生该方案的 API 对照结果。

## 1. 问题与目标

当前初始 query 由模型直接从完整问题生成。已有轨迹呈现出不同情况：qid=1034 将职业、家庭、大学、音乐和职位经历堆入同一条 query；qid=387 选取动画师、无线键盘、纸张规格与日期，首轮就找到包含存储容量的来源；qid=645 则加入原题没有明确提供的 pine，提前缩小了物种范围。

这些情况表明，需要稳定的是线索选择与表达，而非统一缩短所有 query。初始化应当从原题选择一个可搜索入口，准确表达涉及的实体关系，并取得足以开始研究的原文观察。第二个方向是否有价值，需要在同一展示预算下验证。

本节点的目标是提高初始观察的质量，减少无依据的查询限定与条件堆叠。它不负责确认最终候选、解释全部题目约束、维护 gap 或判断何时提交。

## 2. 输入、输出与交接边界

输入是原始问题和实验配置。模型只接收原始问题、初始化指令及要求的方向数量，不接收 gold answer、已有候选、历史检索结果或其他组的输出。qid、随机调度、运行 ID 等由 harness 管理，不需要传给模型。

输出分为两份记录：模型生成的搜索方向，以及 harness 执行 Search 后取得的首轮观察。

```text
原始问题
    ↓
一次模型调用：选择线索、组织方向、表达 query
    ↓
本地格式与来源片段校验
    ↓
固定方向后执行 Search
    ↓
按方向保存原始工具返回与观察账本
    ↓
交给后续研究节点
```

方向选择和 query 表达是两个概念步骤，第一版在同一次 API 调用中完成。不要求模型输出长篇思考，也不增加单独的 planner 调用。

本节点停止在首轮观察，不自动生成 candidate、known_facts、criteria 或 open_questions。原始问题完整保留，未选入 query 的条件没有被删除；后续研究仍可使用它们。

## 3. 搜索方向的数据结构

模型输出一个 JSON 对象：

```json
{
  "directions": [
    {
      "goal": "通过协调员到经理的职位经历寻找人物",
      "source_clues": [
        "this individual was hired for a coordinator position in 2012 and later promoted to a certain manager"
      ],
      "query": "person hired as coordinator in 2012 later promoted to manager"
    },
    {
      "goal": "通过大学专业和音乐经历寻找人物",
      "source_clues": [
        "this individual got into a university between 2001 and 2007 to study Business Administration",
        "The individual also ventured into music, where they released their debut single between 2010 and 2015."
      ],
      "query": "person studied Business Administration at university released debut single"
    }
  ]
}
```

以上是 qid=1034 的格式示意，不是已经验证有效的检索表达。

|字段|含义|约束|
|---|---|---|
|goal|这个方向准备找到什么人物、作品、机构、文章或中间实体|一条简短说明；不能只是“寻找答案”|
|source_clues|方向依据的原题片段|1～3 个非空、连续、逐字摘录的原题子串；不允许使用省略号拼接不连续内容|
|query|实际传给现有 Search 的字符串|独立可理解，保留需要的关系；不以目标答案是否出现为优化目标|

方向 ID、原文位置、生成轮次、解析状态等均由 harness 添加。`source_clues` 属于审计记录，不是永久事实状态；它证明引用了哪些题目文字，不自动证明 query 忠实表达了这些文字。

要求两个方向时，两个 goal 应基于不同的辨识性线索或关系组合。允许共享“演员”“大学”“游戏”等背景词，也允许最终召回同一篇文档。仅交换词序、更换同义词或给同一组线索追加 birth name，不视为两个不同方向。

## 4. 线索选择原则

选择方向时，模型依次考虑可独立搜索、具有辨识度、关系可清楚表达，以及是否需要预先猜测未知实体。

1. 优先使用具体事件、职业变化、明确作品片段、机构特征、关系组合或有辨识度的原文措辞。
2. 每条 query 聚焦一个入口，通常使用一到两个相关线索；必要的主体类型、关系词和时间限定可以一并保留。
3. 可以搜索中间实体。例如先寻找玻璃工艺大师，再由其出生城市关联最终人物。goal 应说明当前要找的中间对象。
4. 不将未经支持的具体人物、公司、物种或作品名称加入 query。“名字像两栖动物的开发商”不能直接改写为某一家具体开发商。
5. 允许翻译、大小写与日期格式转换、常见同义表达；不补充原题未给出的事实性范围，如平台、国家、物种或具体年份。
6. 不为满足方向数量，把明显同义改写包装成新方向。

模型可以省略暂不适合首轮搜索的条件。省略不等于否定条件，也不表示已经满足条件。

## 5. Query 表达原则

当前文档检索使用 Qwen3-Embedding-8B 和 FAISS，文内定位使用 BM25。初始化表达需要兼顾语义关系与可匹配词语，不采用纯关键词压缩作为统一目标。

例如，`mother actress father parliament politician` 容易混淆要找的人及其父母的角色。`person whose mother was an actress and father served in parliament` 保留了关系。这里不预判后者一定取得更好排名，实际效果由固定检索器验证。

时间与关系必须保持原意：

|原题信息|应避免的改写|
|---|---|
|2020 年的文章描述某人就读大学|将 2020 写成入学年份|
|父亲担任议员|将目标人物直接限定为政治家|
|配偶出生于德国|将目标人物限定为德国人|
|大学成立时间在一个区间内|任取区间中的一年作事实限定|
|某属中的一个地中海物种|在没有依据时补入具体属名或物种名|

不要求硬性控制为 4～12 个词。提示词要求一条紧凑的短语或短句；长度只作为运行保护和审计信号。第一版采用最多 512 个 Unicode 字符的 query 硬上限、256 个字符的 goal 上限。超过 240 字符的 query 记录长度提示，但不据此认定质量差。这些数值是初始工程配置，未经效果优化；修改时需新版本记录。

引号不被解释为可靠的精确短语搜索操作符。当前检索路径没有通用网页搜索语法，不鼓励添加 site:、OR 等并未实现的操作符。

## 6. 初始化提示词契约

初始化使用独立提示词，原 Search/Open 工具描述、原文窗口实现和后续 Agent 系统提示词不修改。提示词正文见 [初始化提示词草案](../experiments/query_initialization/INITIALIZER_PROMPT.md)。

提示词要求模型只输出 directions JSON，不输出答案或候选清单。它约束可见输出，不声称能够阻止模型内部产生猜测。

第一版使用普通 Chat Completions 文本响应和本地 JSON 校验，不依赖尚未验证的服务端严格 schema 能力。初始输出上限拟定为 1536 tokens、timeout=120 秒、无 SDK 自动重试；模型和 thinking 沿用当前配置。若联调发现经常截断，应在正式留出集实验前调整并锁定参数，不在看完组间效果后选择性放宽。

## 7. Harness 的校验与失败处理

代码负责检查确定性条件：JSON 结构、字段类型、非空字符串、长度、source_clues 是否是原题子串，以及 query 是否完全重复。完全重复检查只做 Unicode NFKC、大小写和空白规范化，不删除数字、否定词或标点后强行合并语义。

Jaccard 重叠、长度及相同 source_clues 可以用于离线审计，不作为方向独立性的硬判定。实体是否来自猜测、两条关系是否不同，交给人工样本审阅；第一版不另加 LLM judge。

|情况|处理|
|---|---|
|合法输出，数量满足要求|按计划执行 Search|
|要求两条，模型只找到一条|标记 underfilled，只执行实际方向；不强制编造第二条|
|模型输出零条|标记 no_direction，不执行 Search，保留为初始化未取得入口|
|JSON 错误、字段越界、来源片段不匹配、完全重复 query|允许一次受限修复，只提供原题、原输出与具体校验错误；不提供检索结果|
|修复后仍无效|记录 invalid，停止本次初始化，不静默退回整题搜索|
|API 网络错误或响应被截断|记录失败，不从不完整文本中提取部分 query 冒充正常计划|
|Search 某一路失败|保留其他方向结果并标记 partial；不自动产生替代 query|

修复调用计入成本和成功率统计，初次成功与修复后成功分别报告。少方向是允许的语义结果，不触发要求“补满”的格式修复。

同一原题片段可能出现多次。harness 可以保存全部匹配位置或单独记录位置歧义，不让模型猜字符偏移。

## 8. Search 执行与首轮观察

两个方向在第一次 Search 前一起生成和校验。D1 的返回不能用于改写 D2，否则实验变成顺序适应式搜索。底层检索可以串行共享同一 embedding 模型，只有两路调用都结束或明确失败后，才形成交接记录。

本轮固定原有 baseline 窗口，每个文档标题与正文合计最多 400 tokens。不开启 table_entry_safe，不注入观察摘要，不调用 Open，不引入文内 focus。

正式对照使用六个窗口槽位：单方向 top6，双方向各 top3，正文和标题的理论上限均为 2400 tokens。两个方向通常带来额外调用和重复内容，所以实际上下文量、元数据和计算成本仍需记录，不能称为严格相同总成本。

双方向若只生成一条，只执行该方向 top3，不回填剩余槽位；这是预先定义的 underfilled 结果，需在总体统计中保留并单独报告。不将它默默升级为单方向 top6。

不做跨方向重排，也不因为重复命中文档就继续向后补齐“六篇独立文档”。同一文档的不同窗口可能提供不同信息，完全重复窗口则由账本如实记录。这样能够观察方向间真实的重复与互补，不引入额外预算分配器。

交接对象保留原问题、方向 ID、query、各自原始 Search 返回和状态。goal/source_clues 保存为可追溯元数据；后续是否向研究模型展示这些字段，应另行固定协议。调用注明由初始化 harness 执行，不伪装成模型已经自主完成的推理或工具选择。

## 9. 对照实验

|组别|初始化方式|Search 展示预算|
|---|---|---|
|A：当前直接生成|使用现有 Agent 首次请求，取第一个合法 Search query|top6|
|B：单方向改写|独立 initializer，要求一个方向|top6|
|C：双方向改写|同一 initializer，要求两个方向|各 top3|

A 保留原始首个响应及其中其他调用，但本实验只评估第一个 Search query；不执行其他初始调用。若没有 Search，记录 no_search，不追加提示补出一条。模型原请求的 k 与实验实际 k 分开记录。所有组使用相同的实际展示配额规则。

A/B/C 的首次生成采用相同模型、thinking 配置、输出上限、超时和采样设置；不指定采样参数时三组均使用服务端默认。A 保留当前任务指令和工具协议，但也施加本实验统一的输出上限，因此不是逐参数复刻此前未限制输出长度的历史运行。格式修复只适用于 B/C 的结构化输出，其额外成本与首轮失败率单列。

A→B 评估整套初始化提示词与结构化方向表达，不将差异单独归因于 goal 字段。B→C 的指令正文相同，仅方向数量及相应展示配额不同，评估双入口策略。两次重复没有共享模型随机种子的保证，按题目配对并报告波动。

### 9.1 联调与留出集

联调题固定为 1034、645、905、387，分别覆盖条件堆叠、未经支持的范围收窄、人物关系和已有良好入口。先每组一次，共 12 次初始化生成；用于验证格式、原意保持和执行链路，不作为最终效果证据。

参数与提示词锁定后，再从未用于本轮调参的问题中固定抽取 20 题，每组两次，共 120 次初始化生成。正常情况下产生 160 次 Search 和最多 720 个窗口；格式修复等额外调用另计。此数量是第一轮工程验证规模，不声称统计功效充分。

留出集至少排除已讨论的 19 题：186、311、776、324、546、517、1094、580、905、1034、593、177、387、729、496、49、645、1224、802。正式抽样前还需核查已有实验清单，补充排除已用于提示词调参的其他题。这里的留出仅指本地实验未用于调参，不保证未出现在模型预训练中。

抽样种子、题目列表、执行顺序、提示词与源码哈希在运行前保存。若看完留出结果后修改方案，该批题目转为开发材料，不能继续宣称它是未见评测集。

### 9.2 检查内容

|层级|主要问题|记录方式|
|---|---|---|
|生成可靠性|是否得到有效方向；是否需要修复或数量不足|初次成功率、修复率、underfilled 与失败数|
|原题忠实性|是否补入未知候选，改变人物关系、时间、否定或范围|逐方向人工标注，保留原题与 query 对照|
|文档发现|前六个窗口槽位关联的文档中，是否出现可用研究入口|按原题检查原文来源，并标注依据|
|首次观察|实际窗口是否展示足以支持该入口的原文|窗口级检查与来源区间标注|
|双方向贡献|第二方向是否增加有用文档或不同的有效线索|文档、区间和事实三个层次分别记录|
|成本|多一次搜索和结构化生成付出了多少成本|API tokens、修复调用、检索耗时、实际返回 tokens|

精确重复率和区间新增是机械指标，不代替语义价值。两条方向命中不同文档，也不自动计为有效互补。

### 9.3 相关性标注与指标命名

本地 BC+ 的 qa.jsonl 只有 query_id、query、answer，没有完整相关文档标签。不能直接报告全库 recall。答案字符串出现也不能证明文档满足题目关系。

第一轮将各组返回的文档去重后形成联合审阅池，尽量隐藏组别与排名。审阅原始问题及来源正文，记录可用线索和原文位置；随后单独检查各组实际展示的窗口。某文档包含有用信息而窗口没展示，需要与没找到文档分开统计。

标注分三级：0=无关；1=仅主题或宽泛属性相关；2=提供可用于核查某条有辨识度线索的具体事实，或明确的中间实体入口。2 级必须记录“支持哪个线索、对应哪段原文”，不得仅凭出现同一职业或年份赋值。它也不等于最终候选已成立。

主要报告“有用文档发现率”和“有用首次观察率”：各题各次初始化是否至少取得一个 2 级文档或窗口。若统计联合审阅池中的参考覆盖，应明确它是池内覆盖，不能称为全库召回率。窗口存在其他等价支持时，补充标注，不能只因没覆盖某个人工选定的唯一片段而判负。

组别、方向和重复结果在题目层汇总。先报告每题胜、平、负与实例，再提供总体比例；两个重复不视为两个独立问题。双组都有效的子集分析作为补充，全部尝试保留在主表中。

## 10. 验收与版本选择

工程验收要求：来源片段校验、预算、两路计划先于检索、原文与引用、状态及日志均符合契约。不得遗漏失败或把修复成本隐藏为单次成功。

语义验收要求：新 query 没有系统性引入无依据实体或改错关系；原先能够取得入口的题目不能出现明显、可重复的退化。语义标注中的小样本不确定性需要保留，不能由一两个改善案例宣布通过。

B 是否替换 A，由原题忠实性、有用入口取得及成本共同决定。C 是否优于 B，需要额外显示第二方向在固定槽位下提供稳定的有效贡献，足以抵偿每个方向展示深度减半的代价。结果不明确时保留现有方式，不默认升级为双方向。

这一阶段不以 Open 次数、最终回答长度、候选数量或 gap 减少作为通过标准。完整 rollout 可以在局部证据支持后另开实验，不与初始化设计同时修改后续提示词和状态机制。

## 11. 代码与实验目录约定

第一版放在 experiments/query_initialization/，不直接替换 chat.py 或原 Agent 的启动行为。计划文件如下：

|文件|职责|
|---|---|
|INITIALIZER_PROMPT.md|初始化提示词与方向数量参数|
|initializer.py（待实现）|一次生成、JSON 解析、确定性校验、一次受限修复|
|run.py（待实现）|A/B/C 调度、固定 Search 预算、状态和轨迹归档|
|audit.py（待实现）|原文、预算、来源片段、时序与成本核查|
|test_initializer.py（待实现）|关系边界不由代码猜测；测试格式、来源校验、数量不足和错误处理等确定性行为|
|runs/<UTC>/|manifest、题目清单、原始请求响应、实际检索结果、账本、人工标注和汇总|

每次运行记录模型配置、工具与窗口版本、检索模型与索引元数据、提示词、源码、计划方向数和实际方向数。gold answer 不进入生成请求；若离线参考答案用于审阅，应与在线输入明确分离。

## 12. 实施顺序

先实现 initializer 的输出契约与校验，再在四道联调题上检查是否出现线索误写；随后接通冻结的 Search 运行 A/B/C 小样本，确认预算和归因方式可用。最后锁定配置，执行留出集并审阅首轮文档与窗口。

当前阶段的交付是一个可独立评估的初始搜索入口。gap、候选管理和 REPLAN 在该节点之后设计，届时可以复用 goal/query 记录，但无需现在提前建立统一 planner。
