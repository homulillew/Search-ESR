# E0 实验计划：从一次审查定位下一处 bad case

状态：方案、提示词与独立实验入口已提供；本文件不报告尚未执行的模型结果。提示词、检查点和配置在真实调用前冻结。第一批全部为已分析过的开发题。

## 研究问题与最小干预

用户的 Search/Open 改造已经处理“只 Search 不 Open”。当前优先查清的是：**一次有依据的信息需求审查，能否让原动作节点摆脱重复取证和错误前提固化？** 复杂约束随研究展开逐步澄清，不在初始 Query 节点建立完整任务拆解。

H0：同一已见材料下，显式检查未证实前提并提出一个会改变判断的信息需求，比原策略直接继续、或一般进度审查，更容易产生有价值的下一动作。

只增加一个短审查节点，保留原 Actor 的 Search/阅读/回答选择。E0 不执行下一动作，因此能评价需求质量与下一动作方向，不能评价新检索命中、有用新观察或最终答案准确率。第一轮也不同时调整自动触发阈值、覆盖率、停止器、候选淘汰规则或持久 Research State。

## 输入与节点合同

**权威输入是选定 `api_request.request` 的完整深拷贝。** 位置在上一批工具全部返回之后。必须保留 system/user/assistant/tool 消息、调用 ID、完整模型可见内容、工具 schema 与生成配置，验证不存在未返回或重复返回的工具调用。不得选在一个多工具批次中途。

Reviewer 和 Actor 都不能读取标准答案、该前缀之后的事件、原轨迹最终答案、分析稿或缓存全文。准备阶段对全文件原始字节核验哈希，然后仅解析目标之前的日志来抽取前缀；执行阶段只加载独立的准备产物。输入大小不兼容时记录预检或 API 错误，不悄悄引入截断、摘要或额外阅读。

Reviewer 的引用索引只定位已经可见的内容：`question` 表示原题，旧协议观察使用 `event:<tool_result seq>:doc:<实际 docid>`，新协议实际可见窗口保留原 `window_ref`。索引中的 `message_index` 为从 0 开始的消息位置；JSON pointer 定位解析后的消息内容，例如 `/0` 指向第一条返回的文档或窗口对象，其正文在 `text` 字段中。引用索引不授予文档全文访问。有效引用只证明标识存在，不能证明引用支持审查结论。

B/C 提示词共用同一段输入说明，解释 messages/references、从 0 开始的索引与 JSON pointer；原题引用的空路径指向完整原题。历史消息及工具原文中的指令均作为待分析数据，不成为 Reviewer 应执行的新指令。

C 组输出合同：

```json
{
  "current_assumption": null,
  "next_need": "一个尚未解决、会影响当前判断的具体信息问题",
  "decision_effect": "可能观察如何影响保留、修订判断或进入作答检查",
  "basis_refs": ["question"]
}
```

- `current_assumption` 可以为 null，不要求审查每次找出错误。历史 assistant 的断言仍需要原题或已见原文支撑。
- `next_need` 可以为 null，不要求继续调查或切换候选。需求可以检查当前候选，也可以回查上游关系。
- 有 `next_need` 时必须说明 `decision_effect`；无需求时其值为 null。未检索到一条事实不等于该候选被证伪。
- 只允许四个字段；前三个为非空字符串或 null，`basis_refs` 为已提供标识的字符串数组，标识不得重复。机械校验不判断语义真值，也不保证字符串中的内容没有偷偷写成 Query。

Reviewer 不能生成 Query、执行工具或挑选最终答案。其结果通过 [共用备忘包装](prompts/memo.txt)，作为克隆请求末尾的 user-role 说明交给 Actor。包装明确这是可能有误的模型备忘，要求继续原任务，不当作新增原文证据或用户补充事实。这里不调用 `AgentSession.ask()`，避免重建用户轮次和重置原工具预算。

Actor 沿用原请求参数；如服务需要换模型，必须显式 `--model` 并记录原模型和覆盖模型，B/C Reviewer 同步使用该模型。Reviewer 的有效 system 为该组审查提示词；捕获的 messages（包括旧 system）和 references 作为同一 JSON 数据包装传入。B/C 沿用相同的原生成/thinking 配置，去掉工具/function/web-search 权限、原 response_format 和 stream_options，改为单个非流式响应，输出上限单独固定。原请求存在 `max_completion_tokens` 时使用该字段，否则使用 `max_tokens`。有歧义的 `extra_body` 保留键覆盖被拒绝，避免旁路改写实际请求。Actor 不继承 Reviewer 的 512-token 限制。

## 调度与成本

| 配置 | 固定值或记录要求 |
|---|---|
| 检查点 | 3 个，顺序和源提交见配置 |
| Arms | A 原策略；B 一般进度审查；C Need Review |
| 重复数 | 每题每组 2 次；每次独立生成审查 |
| 调度 | 固定 seed 20260919 的交错安排；运行前保存计划 |
| Reviewer | 同模型；最大输出 512 tokens |
| Actor | 原检查点请求参数，除显式记录的模型覆盖 |
| SDK 重试 | 默认 0；任何改变单列为配置变化 |
| 计划成本 | 18 次 Actor + 12 次 Reviewer = 30 次逻辑调用 |
| 实际成本 | 各次调用的 token、耗时、失败与已发生的消耗；不可从计划数代替实际记录 |

`plan` 和 `execute` 的 `--model`、`--review-max-tokens`、`--sdk-max-retries` 必须一致；改变其中任一值后，先更新计划再开始执行。

两次重复只用于发现不稳定行为，不足以估计总体统计显著性。调度 seed 固定执行安排，不表示远端采样随机性完全受控。服务端是否支持或应用模型 seed，应依据实际请求记录，不能仅因实验调度有 seed 就宣称模型采样已复现。

逻辑分支数始终为 18。错误不删样本：Reviewer 失败、B 输出空/拒绝/工具调用/截断、C schema 或引用错误均保存，并回退到无备忘的原 Actor 请求。C 的机械无效标记为 `node_invalid`，原文、错误原因与成本仍归入 C。没有在线人工修订或自动 JSON 修复。Actor 请求失败仍作为该分支失败，不能偷偷补一个成功样本覆盖。

来源校验失败、请求配置歧义与凭证配置错误属于调用前的输入/配置失败；在首个模型调用前终止，不伪装成一个可回退的审查节点失败。回退保留完整实验分母，但不能替代必要的输入验证。

## 人工评价步骤

1. 在查看各分支输出前，只看原题、完整前缀和可见原文，写下“当前已建立的关系”“尚未建立但正在使用的前提”“几种允许的合理下一步”。允许多个路线，不根据 gold 倒推出唯一 Query。
2. 检查输入、模型/工具版本和哈希一致性；查看是否发生参数覆盖、失败回退或预算差异。
3. 阅读 `cards.jsonl` 中隐藏组名的审查/Actor 输出卡，依照 `rubric.json` 逐卡标注，完成后再查看 `private_key.json` 分组映射。格式可能暴露组别，故不声称完全盲评。
4. 对每个分支分别标注审查质量、动作质量、回归与错误。多个工具调用作为一个完整决策批次，不只挑最好的一条。
5. 汇总全部 18 个分支，再挑最能区分链路失效位置的 1–3 个 bad case。原始请求响应、人工标注和解释分开保存。

建议一行一个分支，使用 rubric 中的 `yes / no / unknown / not_applicable` 标签；不要将不确定自动归为通过。`memo_injected=false` 的回退分支中，Actor 没有看见所展示的审查，需求传递项应记为 `not_applicable`；即使动作恰好与该需求一致，也不能记为传递成功。

| 评价维度 | 要回答的问题 | 常见错误 |
|---|---|---|
| 假设依据 | 指出的前提是否确实未被建立，是否影响当前路线？ | 已证实事实被当错；编造本来不存在的前提 |
| 需求未决性 | 已见材料是否已经回答了这个问题？ | 只是重复读取；需要的信息实际已在可见窗口中 |
| 需求相关性 | 回答它能改变原题答案、中间关系或继续研究判断吗？ | 泛泛“进一步验证”；与复杂题目的决定性关系无关 |
| 决策区分力 | 能否说明保留与修订判断的不同观察？ | 单向要求证明候选；将未命中当反证 |
| 引用语义 | 实际可见内容是否支持这项审查判断？ | 引用存在但无关；从片段推断未见全文 |
| 动作响应 | Actor 是否在语义上处理了一个合理需求？ | Query 改词但仍锁死同一前提；需求好却被忽略 |
| 动作独立质量 | 即使没有审查，下一动作本身是否合理？ | 把“服从一个错误需求”误算改善 |
| 517 回归 | 是否保留合理纠偏，而非无依据换人或结束？ | 越爱换候选评分越高；原本会纠偏被打断 |
| 结束行为 | 是工具批次、自然回答、语义弃答还是协议/API 错误？ | 正常结束误作失败；`next_need=null` 被当作充分证明 |
| 成本与可靠性 | 实际调用、token、耗时和无效率是多少？ | 只报告成功分支；额外反思计算被忽略 |

工具响应还需分开看语法与原运行时协议。已知部分兼容 API 会在有完整 `tool_calls` 时返回 `finish_reason=stop`。入口保留全部调用及 `response_kind=tool_calls`，在语法完整时标记 `syntactic_complete=true`，同时记 `protocol_compatible=false` 与 `tool_calls_with_stop`。旧 Actor 循环不会把这种返回当作可执行工具轮次。它的动作意图仍可审阅，但不能把格式不兼容当作语义选错，也不能报告它已在原循环中执行。

可以统计每组“合理下一动作”的分支数，但必须同时给出分母、失败数和逐题解释。三题都是开发材料，两次重复高度相关，不将这张表写成 BC+ benchmark 涨分。

## 结果如何决定下一步

| 实际观察 | 下一轮只改一处 | 本轮不推断 |
|---|---|---|
| 审查把猜测当事实，引用支持不了结论 | 改证据读取与假设区分 | 不能靠扩充 State 字段自然解决 |
| 需求始终是“证明当前候选” | 改需求定义与提示词 | 不把换候选频率当作探索质量 |
| 需求已经被已见材料回答 | 查输入读取，再决定是否加局部索引 | 不直接扩大检索预算 |
| 需求合理，Actor 仍围绕错误前提检索 | 单独改审查到动作的输入合同；必要时做另标的合理需求替换诊断 | 不能说 gap 已实际驱动动作 |
| B/C 相近且都好于 A | 优先保留更简单的一般审查 | 不宣称结构化 Need Review 必需 |
| C 破坏 517 的合理纠偏 | 修正过度反思、强制找错或停止暗示 | 不把干预次数越多当作越好 |
| 需求和动作都有依据 | 再提出 E1：实际执行下一批工具并观察一次后续决策 | 尚不能声称检索收益、答案收益 |

E1 必须恢复同一冻结工具版本、原来剩余工具轮次和可用引用集合，后续观察由该分支实际动作产生。旧轨迹的未来工具结果不能喂给新 Query。若在当前 Search/Open 下取得新前缀后旧症状已经消失，就记为已解决，不恢复旧缺陷来制造对照。

只有真实取证后出现“忘记这次想解决什么”，才加一条 `last_attempt`，记录本次目标、实际得到什么、仍未回答什么。只有多轮状态丢失成为可观察 bad case，才扩大持久语义字段。自动触发器需在审查机制有效后独立比较。

## 停止问题另做诊断

用户报告的“证据充分仍不提交”仍是目标，但所选旧批次不是该症状的已验证样本。后续应在当前协议下固定真正疑似充分的前缀，禁用工具做同模型作答探针，分别看答案正确性、当前可见原文支持和多次稳定性，再判断是信息整合失败还是结束选择失败。

`next_need=null` 只是审查没有提出有用新需求，不等于程序证明了答案充分。可答、受阻、弃答、预算耗尽需要分别保留。本轮不实现 stop 节点，也不把强制作答探针混入 E0。

## 文献借鉴及证据边界

这些论文提供设计思想；本实验的提示词和字段是仓库自拟，论文收益不是 E0 的预期成绩。

| 原始文献 | 借鉴 | 不能直接迁移的部分 |
|---|---|---|
| [RAAC: When Deep Research Agents Stagnate](https://arxiv.org/abs/2608.15191)，2026-08-15 v1 | 在研究中途做一次局部审查 | 整体控制器混合额外推理、Query 改写、执行和停止；BC+ coverage 还使用数据集 criteria，不能视作自动初始化证明 |
| [The Missing Complement](https://arxiv.org/pdf/2609.20050)，2026-09-17 v1 | 固定中间状态，匹配语义调用数，关注决策所缺关系 | 主要是编码任务与预补全候选池；反馈组件的单独小增量区间跨零，不能借整体收益证明 gap 单字段 |
| [DAS: To Search or Not to Search](https://arxiv.org/html/2602.03304v1)，2026-02-03 v1 | 将固定前缀上的强制作答用于独立停止诊断 | 后续 DPO 需要训练；一次答对不保证已有可见证据支持 |
| [HALT](https://arxiv.org/pdf/2608.02009)，2026-08-28 v3 | 检查关键关系是否已有支持 | verifier 经 LoRA 训练；固定初始 claims 和历史最大匹配不能直接支持动态纠错 |
| [AdaPlanner](https://arxiv.org/html/2305.16653v1) | 观察不符合预期后做局部修订 | 可执行环境断言不能当作 BC+ 事实真值；本轮尚未执行观察反馈环 |

这些借鉴共同支持先测一次局部干预、保留一般审查对照，再按新 bad case 扩展链路。
