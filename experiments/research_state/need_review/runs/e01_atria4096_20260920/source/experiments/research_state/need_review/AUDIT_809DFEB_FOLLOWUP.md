## 1. 结论：接线基本成立，不等于研究控制成立

根据[原始报告](runs/e0_20260919T171923Z/REPORT.zh-CN.md)，本批18分支、30次模型调用、0工具执行；15条Search、3条最终答案；18条Actor响应兼容旧协议，无API错误，1条C审查截断并正确回退。完整响应可接受A/B/C均0/6；局部Query方向正向0/1/2。总reported tokens为855,560，不是费用账单。这些数字不能换算成检索命中率或BC+准确率。

当前证据更支持以下分层，而不是在“harness坏/模型弱”之间二选一：

| 层次 | 观察到的问题 | 能支持的归因 |
|---|---|---|
| 机械执行 | 原批请求、回退、完成原因基本符合合同 | 没有证据说漏传备忘或禁用工具解释本批语义错误 |
| 来源解释 | Reviewer把历史猜测、局部关系或原题条件扩大为候选满足条件 | 上游审查有真实模型错误；输入和解释合同也有可改进空间 |
| 关系修订 | 假定中间实体不匹配，被推成整个候选必须淘汰 | 作用域/关系推理失败，不是字符串Query去重问题 |
| 需求到动作 | 有合理提醒，Actor仍沿旧路线调查 | 不能把所有失败归给Reviewer；软备忘尚无稳定的决策作用 |
| 停止 | 非空需求和可用工具下仍最终作答 | Actor的证据充分性判断失败，不是程序把null需求当停止 |
| 模型能力 | 该模型配置下确实发生上述失误 | 单模型别名、thinking关闭、长历史、三个开发题不能证明能力上限 |

## 2. 关键 bad case 的链路

### 546：应回退的可能是赛事绑定，而不是人选

[原始C/r2](runs/e0_20260919T171923Z/branches/qid_546_s29__C__r2/result.json)把目标赛事预绑定为2023 Players Championship，随后规定Selby在该赛事记录不符就必须排除Selby。

但原题尚未把那条比赛序列绑定到该赛事。逻辑上：`¬R(候选X, 假定赛事Y)` 不能推出 `¬∃赛事Z R(X,Z)`。失败可能来自候选，也可能来自赛事、年份、轮次的绑定。若仍沿同一错误赛事换人，词面Query虽然不同，研究前提没有纠正。

原材料对转职业时间等局部属性的支持，也不能证明同一人的完整比赛路径。引用ID合法只说明指向可见对象，不证明对象支持所有伴随断言。故首改来源/关系范围合同，而不是强制换候选。

### 776：合理提醒被忽略与无效审查回退是两回事

[原始B/r2](runs/e0_20260919T171923Z/branches/qid_776_s53__B__r2/result.json)正确指出anthropologist/folklorist职业假设缺乏观察支持，Actor仍重复职业导向查询。这是下游未合理使用提醒的证据，不能简化为上游全错。不过，用职业作一次探索假设本身未必错误；问题是重复无进展路线并把假设重新确定化。

[原始C/r1](runs/e0_20260919T171923Z/branches/qid_776_s53__C__r1/result.json)则输出大量basis_refs，512-token上限处JSON截断。它没有作为备忘传入Actor，回退是正确行为，不能记为“有效gap没驱动动作”。如果只统计有效审查，会丢掉方案真实可靠性成本。

该例也显示“找出未证实前提”与“生成能区分判断的下一问题”并不等价。重述整套人物传记约束，可能仍不能提供比原问题更有用的调查方向。

### 517：为了保住候选而放松原题

[原始C/r2](runs/e0_20260919T171923Z/branches/qid_517_s21__C__r2/result.json)允许policeman被宽松解释来适配候选。引用实际只覆盖部分导演/作品线索，尚未支持家庭和角色关系。Actor之后未得到任何新工具观察就最终作答。

这里next_need非null、工具可用。因此不是缺少submit函数，也不是runner触发预算结束。根因是把若干局部关联扩成整条链成立，又把冲突解释为题目有误。应修订解释和绑定，而不是更改题目条件。

另需纠正“正控”表述：本批两个A仍保留1975硬过滤，原历史曾纠偏不等于当前重放A稳定成功。能确认C/r2出现提前无支持提交，但不能称其破坏了本批一个已正确的基线答案。

## 3. harness 实现是否标准

不存在一个第三方框架可以自动保证研究语义正确。应分别核对API协议、实验合同和研究语义。

原E0合理之处包括：固定原请求；完整工具调用配对；Reviewer没有工具权限；引用只来自已见观察；深拷贝A请求；B/C同模型和审查cap；无效审查回退；保存所有失败；不把completed判为正确。JSON Schema子集检查器也不能冒充任意真实backend的完整验证器。

原E0的局限包括：Reviewer得到引用定位索引，Actor只得到引用名字和备忘；备忘是追加到完整历史的软建议，并未撤销原有猜测；计划打印与执行之间原本缺少强约束；导出需要核对实际请求而非只核对checkpoint。859e0f1已补充这些机械能力，详见[AUDIT_20260920.md](AUDIT_20260920.md)。

尤其应保留859的选择：引用索引交接属于可选的`indexed_json_v1`，当前来源合同配对仍用`legacy_text`，不能同时改变输入包装与来源规则后声称单点归因。引用缺交接是潜在定位障碍，但没有证据证明它导致这次全部错误。

停止也不应急着接管。现在已有证据不足就提交的病例；立即降低停止门槛可能加重错误，强制继续又可能遮蔽它。停止充分性应另选当前Search/Open下确实接近答案的检查点做立即作答诊断。

## 4. 本次额外复现并修复的成本边界

859已修复809中`usage={}`被漏标缺失的问题。本次没有重复覆盖该修复，而是补充两个边界：

1. `prompt_tokens=2, completion_tokens=1, total_tokens=99` 三个字段都有合法整数，旧859总结仍会给`cost_accounting_complete=true`。修订后为false，并记录`responses_inconsistent_usage=1`。
2. usage只有部分合法字段时，原859丢掉整条的所有计数。修订后保留合法的**已报告部分值**，明确缺失字段，不推算不存在的total，更不补成零成本。

新增 `accounting.py` 的 `inspect_usage` 拒绝布尔/负数/非整数计数，检查总数恒等式。`run.summarize`增加 `responses_inconsistent_usage`、`missing_usage_fields_by_stage`，并纳入`cost_accounting_complete`；未知stage另列record error。分组成本保持by_arm/by_contract；部分计数绝不是完整账单。原始响应不改写。

成本异常不自动等价于语义错误：可保留正确动作作语义分析，但不能据它计算完整成本收益。费用仍受provider口径、缓存和实际计费规则影响。本检查只针对Chat Completions报告字段，不推断货币价格。

[合成故障复现记录](accounting_regression_probe.json)固定旧859源码blob `2726b42d33fe4e34501270609ef6f92e92bb195d`。该问题没有在原855,560-token记录中被证明发生，因此不能当作原bad case的成因。

## 5. 最小下一实验仍只改来源归属

使用已有 `--comparison source_contract_pair`：C0原prompt，C1 `need_review_source_grounded.txt`；3题×2次×2组=12分支，24次逻辑调用，零工具执行。来源规则已针对上述病例区分：题目目标、已见原文、assistant假设；局部支持和完整关系；未证实绑定和反证。

保留512-token cap、同一四字段schema、同一原始payload、同一memo/Actor、同一工具版本。不要再合并另一套runner、加引用硬截断或停止器。用同期C0而非旧成绩作对照。这个实验只能检验来源规则处理包，不能证明结构化gap优于一般反思，也不能把提示词变长产生的全部效果归给某句话。

先看Reviewer来源归属是否改善，再看需求是否合理、Actor是否使用，最后分别看工具动作和前导事实断言。保留原完整响应可接受指标，避免通过只看Query末行人为制造涨分。无效审查保留在分母，未注入不评需求服从；unsupported不自动等于答案名字错误。

Reviewer正确而Actor仍不响应时，下一轮固定正确需求，只调交接；Reviewer仍混淆时，才比较同一证据库存的来源分层视图；两者都合理后才进入真实工具E1。真正的模型能力比较应在相同输入、工具和总计算条件下另做，不与本轮混在一起。
