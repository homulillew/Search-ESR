# 表格入口结构修复：预设方案

唯一改动：Search窗口已进入Markdown表头、但尚未完整展示第一条数据行时，尝试在同一400-token标题+正文预算内包含表头、分隔行和首条数据行。只从窗口左侧裁减扩展上下文，必须保留原定位器经结构修复后的完整锚点，按已有原文单元边界裁减；无法同时满足则原样返回。原文连续，不增加语义生成、query重排、身份识别或模型可见字段。Open保持原实现，不改变围绕已有窗口的扩展语义。

候选实现只放experiments，冻结生产文件不修改。结构修复不承诺首行就是答案。本次不处理任意章节标题或表内所有行，避免同时引入多个策略。

离线对照：复用20个局部需求，以及此前16次真实会话的610条返回，固定其query/docid。分别报告原始出现次数和去重query/docid结果；610返回受重复搜索影响，不能视为610独立样本。检查预算、原文连续性、锚点保留、表格入口完整性、丢失的左侧原文、原有参考片段可见性。离线标注不送入定位器或API。

API对照：沿用此前6个明确主体的局部需求，每例每组3次，共36会话。基线使用冻结窗口，候选使用结构修复窗口；相同原始系统提示词、TOOLS和API配置，最多4轮后续调用加一次终答。预置同一文档的两种真实窗口，模型自主回答、Search或Open，不强制读取。后续Search也按所属组返回窗口，Open不变。定位器与retriever相同，窗口范围是唯一处理因素。

主要检查是否取得具体角色及其原文依据，已有充分信息的控制是否受损，新增答案是否仍伴随无依据扩展。Open次数不是成功指标。本批是既有坏例回归，不能据此声称普遍泛化。只有明确改善且无已见回归时，才讨论是否独立升级生产版本。
