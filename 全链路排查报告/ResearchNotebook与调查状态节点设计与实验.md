# Research Notebook 与调查状态：节点设计及最小实验

状态：实现与离线验证完成；尚无本方案真实模型结果。基点：`396592c3ed371a6be260ca0a40434d1f6afc821f`。

## 1. 本阶段要回答什么

在冻结的原题、实际观察、历史分析、研究笔记和调查问题都相同时，**改变它们的呈现结构，是否改善下一决策？**

第一实验 S0 比较扁平清单和按来源/职责分组的视图。第二实验 S1 单独比较是否提供机械生成的历史尝试关联索引。两者不能混成同一个 treatment；默认只执行 S0。两种实验均一分支一 Actor 请求，没有 Reviewer、工具执行、自动状态抽取或在线修复。

这是“固定内容的状态视图编译节点”，不是完整 Research State 的最终架构。固定笔记由助手根据已知前缀编写，知道历史 bad case，正式调用前必须逐项核对。**不能把夹具的人工/助手整理能力记成自动 harness 收益，不能把这三题当留出集。**

不再限定必须复现 ESR 的 Finding/Claim/Gap 图。先把研究内容、当前调查及机械执行记录分开，让下一轮错误决定是否需要依赖图和持久更新。

## 3. 与已有节点的关系

```text
原题 → 既有 Query/检索 → 已见原文与历史
                               ↓
                    固定研究笔记、一个调查问题
                               ↓
                 本节点：无损编译 ResearchPacket
                               ↓
                     Actor 的一次下一决策
                               ↓
                  停在这里；记录提议，不执行工具
```

Search/Open 的定位、展示、窗口预算与原文引用不改。初始 Query 方案不改，第一步不强制产生所有候选/条件/gap。这里的任务夹具来自研究已展开的检查点，不是开局规划要求。

采用“双账本”区分内容与进度、用历史尝试辅助路线调整、按需要生成工作视图。相关讨论来源包括 [Magentic-One](https://arxiv.org/abs/2411.04468)、[IterResearch](https://arxiv.org/abs/2511.07327)、[RE-TRAC](https://arxiv.org/abs/2602.02486)、[Table-as-Search](https://arxiv.org/abs/2602.06724)。本实现只借鉴职责拆分，不是这些论文的复现，也不引用其效果作为本方案的预期提升。

## 4. 输入与状态合同

### 4.1 原始材料

直接读取仓库已经保存的、只包含检查点之前内容的独立 checkpoint JSON；prepare 检查原始文件 Git blob 哈希，再复用既有 `load_checkpoint` 完整校验。它不读取旁边的答题结果、Reviewer 输出、gold、未来日志或完整语料库。

只支持一个原始 user 问题且检查点位于完整工具批次之后。多用户追问暂不支持，显式拒绝，不猜哪个 user 才是当前问题。所有原始 messages、完整 tool content、tool call、角色和来源引用逐对象保留；既不删除有害历史分析，也不加入未见原文。

`mN` 恒指原始消息 N。分组改变的是显示位置，不能改变 `message_index` 的含义。工具引用的 JSON Pointer 仍指向该原始消息的 JSON-decoded content。单次窗口而不是整篇缓存文档是引用授权边界。

### 4.2 固定研究笔记

笔记每条仅有 `kind / text / basis`：

| kind | 含义 | 机械限制 |
|---|---|---|
| given_constraint | 原题对未知目标的要求 | basis 必须指原题 |
| observed_finding | 对显示原文的有保留解读 | 必须有 tool 来源，不能用原题/assistant 作为该事实证据 |
| hypothesis | 搜索过程中的候选或绑定假设 | 可引用历史 assistant 的确切文字；不升级为事实 |
| unresolved | 当前笔记未解决的关系或冲突 | 必须给出相关可见依据，仍需人工判断范围 |

`basis` 是 `ref + quote`，或针对历史假设的 `message_index + quote`。quote 必须是该可见文本的连续子串，代码不进行模糊修复、自动补引文或全文查询。机械检查不能证明 text 由 quote 蕴含；测试专门保留“引用是真的但主体被错绑”仍可能过结构检查的例子。

夹具中没有标准答案，笔记不是金标事实状态。数量和字符上限是工程保护，不是效果最优参数。没有相关发现时可以留空；不要求填满一张大表。

### 4.3 一个当前调查问题

`task` 为 null 或：

```json
{
  "intent": "verify",
  "question": "当前候选与指定角色的关系能由哪个已见或待查来源建立？",
  "decision_effect": "可靠角色记录可以支持或修订该绑定；没有搜到不能自动排除整个人选。",
  "basis": [{"ref": "question", "quote": "原题中的真实连续文字"}]
}
```

这是格式示意，不是可直接用于三个病例的夹具。支持 discover/verify/clarify 三种局部目的，不在此节点生成 query、答案或多个后续计划。null 不触发提交。任务由夹具固定，所以本轮**不检验自动 gap 生成，也不证明 gap 的因果作用**。

### 4.4 调查尝试

程序遍历真实工具批次，记录调用名、完整参数、call ID、原始消息位置及返回引用。`delivery=recorded_tool_response` 只说明返回已记录；`information_gain=not_evaluated` 明确不作语义评价。工具返回 error/空列表也保留。

S1 的可选索引提供两类关联：

- 工具名＋JSON 参数对象完全相同；Query 字符串不做小写、空白、同义词或模糊归一化。
- 按顺序返回的可见文本/主体/URL/位置相同；忽略检索 score 和每次事件引用名称。

同 docid 的不同窗口不合并；同样内容因 score 改变不算新观察。索引不删除重复记录、不拦截动作、不判断候选真假，也不认为两次同一来源是两份独立支持。

错误关系撤回、反证与新入口也可能是进展。不能由新增字符、条目数量或这个机械索引替代研究进展判断。

## 5. 两个互斥对照

### S0：layout，首先运行

- F/flat：按原顺序给完整消息，随后笔记、调查任务和尝试记录；每项保留相同类型标签。
- T/typed：同一份条目按原题、笔记类别、任务、尝试、原文、历史分析、历史指令分组。

两组 Actor system 提示词、模型/profile、工具定义、笔记文本、问题、原文、引用、历史猜测、尝试记录完全相同。编译器能从两种视图还原同一条目清单和原始 messages。

F 不是故意剥夺来源标签的弱基线。T 改变了分组、位置与注意力分配，因此结论是**呈现方式整体**的效果，不是 JSON 一定优于自然语言或某个字段单独有效。实际输入 tokens/scaffold 长度不同，按真实 usage 报告，不称等 token。

### S1：attempt_linkage，只在另立计划后运行

- T/typed：上述分层视图。
- L/linked：T 完全不动，只增加由相同尝试记录计算的索引。

它测的是给模型显式计算辅助的效果，不是增加新的外部证据。不得在 S0 的 treatment 中偷偷启用索引。

两种实验默认都是 3 前缀 × 2 组 × 2 重复＝**12 Actor 调用**，0 Reviewer，0 工具执行。pilot 使用一次重复＝6 Actor 调用，独立保留且不混入正式分母。没有 A/C0/C1 名称复用，以免将旧 Reviewer 对照的含义带过来。

### 不允许的归因

两个臂都获得同一份固定笔记。即使 T 优于 F，也不能说自动状态更新有效；两者都差，也不能说研究笔记比原历史差。与原始 Actor 的架构比较需要另外添加同期原历史基线，本轮没有实现该比较。

当前 Actor system 是新实验的共同合同，全部历史消息被序列化为数据；工具定义保持捕获版本。不能说与旧 E0 的 Actor 输入完全不变，也不能跨旧批次用分数差归因视图。

## 6. 新 API 接入与交付先验收

`profile.example.json` 是**未经本次实调验收的候选配置**：Atria、max_tokens=8192、SDK timeout=180 秒、2 MB 请求字节保护。它不是宣称这些值最优，也不假定 max_tokens 只限制正文。reasoning 可能消耗额度。

不从旧 checkpoint 继承 `enable_thinking=false`，不读取环境变量暗中改变模型或地址。profile 明确模型、无凭证 base URL、超时和允许的请求选项。仅可选择一种 token cap；支持显式 reasoning_effort，但不声称服务商支持任何给定取值。未知自定义 extra_body、凭证、tools/messages 覆盖均拒绝，需在独立接入变更中验证再扩展。

先运行独立 pilot，检查每个臂的完整交付、工具参数和成本。若 reasoning-only/length、超时或协议不兼容，保留全批，先做接入诊断；不转投更强 Reviewer、不从 reasoning 拼 JSON、不在线修参数、不重复采样直到成功。

正式计划需要：同 bundle/profile/代码/提示词/实验类型的 live pilot 经离线审计交付干净且成本已知；以及绑在 bundle 哈希上的夹具复核声明。pilot gate **不读取语义分数**，不能按动作好坏筛选正式样本。小 pilot 不是服务 SLA；模型别名仍可能漂移。

SDK timeout 是客户端超时配置，不保证严格总墙钟上限。序号/超时/截断/工具协议/未知成本分别统计，超时无响应不能当成零消耗。

## 7. 实现及留痕

代码：`experiments/research_state/investigation_state/`。

- packet.py：来源校验、固定笔记合同、完整尝试、无损渲染及机械重复诊断。
- run.py：prepare/plan/execute/audit，单模型下一决策，无检索器导入。
- report.py：实际请求与冻结请求逐对象核对、事件/结果对应、阶段分母和人工卡片。
- storage.py：严格 JSON、目录边界、原子 fsync 写入、损坏日志只恢复连续前缀。
- fixtures.json：三个开发夹具、原始快照路径和 Git blob 哈希。
- prompts/actor.txt：三种视图共用的决策合同。

复用既有 checkpoint 校验、Actor 协议分类和 token 记账函数，旧模块不改。计划冻结 bundle、fixture review、模型与端点、预算、超时、采样选项、调度、提示词和相关源码及 Python/SDK 版本。execute 没有运行中覆盖参数，使用一次加载的输入快照并为客户端深拷贝。

保存所有 request、raw response、错误类别、耗时、完整工具批次、源码副本及 summary。异常字符串/HTTP 响应体可能包含凭证，错误日志不保存这些内容。SDK retries 固定0。不能把 `finish_reason=stop` 的工具提议静默改为 tool_calls；意图保留，捕获协议兼容性单列。

没有结果文件时可从日志恢复已收到的响应，但标为部分记录，不冒充完整执行。未知成本请求、usage 缺失/算术不一致、日志损坏分别保留。只输出机器 summary，不自动生成“动作好坏”分数。

## 8. 逐节点评价

先读不含输出的 prefix_cards，写合理的多种下一动作，再看完整交付正文和全部工具调用。最后对照 private_key。作者知道旧案例，视图也可能暴露分组，因此不称严格盲评；不重跑脚本伪造首评时间。

主指标保留完整下一响应是否合理，诊断轴分开：来源归属、关系作用域、是否实际使用调查目的、工具方向、重复是否有新目的、正文支持、最终答案支持、新错误。非法协议/未交付输入下不评价不存在的来源能力；不要把失败从分母删除。

完全相同参数重复只作标记；一个看似相似的新 Query 可能是合理扩大召回。原题部分条件未写入该次 Query 也不必然错误。只要没执行工具，就不能报告新增召回/证据覆盖/最终正确率。空正文加合法工具提议是允许的；不是所有调用都必须输出一段解释来获分。

任务使用要检查决策目的，而非同主题词。S0/S1 的 task 固定，不做因果替换；后来可独立设计两种同样合理任务的干预。不能从这轮的相关性标签证明 gap 因果驱动。

## 9. 根据结果决定下一节点

| 结果 | 下一步只改哪里 |
|---|---|
| 大量 API/交付失败 | 独立接入/profile 验收，不改状态语义来掩盖 |
| F/T 都混淆原文主体或来源 | 单独做“观察→笔记”的局部读解，不增加字段数量 |
| T 更稳定保留关系而动作仍重复 | 单独运行 S1 尝试关联索引 |
| 有调查目的但 Actor 将其未来验证条件当事实 | 单独调需求到动作/证据使用合同，不要求无条件服从 |
| 合理动作出现，未知真实取证效果 | 冻结当前版本，另设计 S2 真工具执行并检查新观察 |
| 笔记/尝试状态确有帮助，自动写入尚无证据 | 固定旧状态和新观察，只测试局部增量更新与撤回 |
| 两组差异不清楚 | 保留简单版本，加独立局部病例；不据小样本堆图/多Agent |

持久候选表、依赖图、自动停滞触发、观察摘要、独立 Verify、停止器与训练均不在本次实现范围。未来需要提交时，区分“原题必要条件已足够支持”“当前路线受阻”“预算结束”；不能要求所有自发背景问题清零。

## 10. 验证与当前结论
