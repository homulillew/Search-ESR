# Search 动作优化：从文档开头截断到相关片段定位

> 本文保留各阶段的逐轮记录，早期“当前方案”表述对应当时状态。完整节点结论、最终职责边界和冻结范围以 [Search–Open 节点排查与冻结报告](Search-Open节点排查与冻结报告.md) 为准。

本文记录 Search 动作的逐步排查与优化。当前完成的是第一步：在保持文档检索结果不变的条件下，将固定返回文档开头改为按 query 选择文档内片段，并进行离线对照。

本轮实验已经能够将部分后文交付到返回结果中，但也出现了实体匹配不完整、事件时间不符和上下文缺失。因此，当前原型尚未接入在线 Agent，也没有新的答案正确率结果。

| 阶段 | 改动 | 状态 |
| --- | --- | --- |
| 原始方案 | 文档向量检索，返回前 1600 字符 | 已完成真实 rollout 和 bad case 分析 |
| 实验一：相关片段定位 v001 | 段落分块、文档内 BM25 排序、单片段返回 | 已完成离线对照 |
| 下一步：补充上下文和改进切分边界 | 检查人物身份、标题、表头与比赛记录的完整性 | 待设计与验证 |

后续 Search 优化继续在本文补充，分别记录每一步的改动、对照结果和剩余问题。原始轨迹与离线产物保留在独立实验目录中。

## 1. 原始 Search 方案

当前 Agent 使用 Qwen3-Embedding-8B 将 query 编码为向量，与本地 100,195 篇文档的预计算向量进行 FAISS 精确内积检索。默认返回 top-5 文档，再从 SQLite 读取对应全文。

真正交给模型的内容由工具封装决定：每篇文档只保留前 1600 字符，同时返回 docid、URL、文档分数、总字符数和截断标记。

```text
模型生成 query
      ↓
文档级向量检索
      ↓
取 top-5 文档全文
      ↓
每篇截取前 1600 字符
      ↓
模型根据片段决定下一步
```

这里的文档级向量不代表编码时一定覆盖了文档全文。当前实验不修改或重新编码这些向量，只检查检索后的内容交付过程。

如果模型需要后文，可以调用 `get_document`，默认读取 8000 字符，并通过 offset 继续翻页。但接口没有页内关键词查找或相关段落定位能力，模型需要自行决定是否读取以及从哪里读取。

这个方案实现简单，能够控制单次返回量。不过，同一篇文档无论被哪个 query 命中，Search 都返回相同开头。文档检索与片段展示之间没有建立对应关系。

## 2. 从真实 bad case 定位问题

64 轮预算批次中，六题全部在预算耗尽前主动结束。其中五题没有调用 `get_document`。单看这一计数，无法判断模型是否缺少必要阅读：有些题目的搜索片段已经足够，有些题目连相关文档都没有召回。

本轮选择 546、1094 和 517，是因为它们能分别展示长文证据不可见、事件定位困难和已有成功路径。相关分析基于实际工具返回，不将离线查看的全文当成模型已经读过的内容。

### 2.1 qid 546：相关比赛文档已经召回，后文没有进入观察范围

模型多次检索到 84585《2023 British Open》。全文长 52,592 字符，开头主要是决赛和半决赛记录。与题目相关的部分比赛记录位于文档末尾，远超前 1600 字符。

模型后续仍持续搜索，没有转向文档阅读。最后五次搜索都没有新增 docid，最终将未经工具证据支持的比赛链写入答案，回答了错误候选 Mark Selby。

这条轨迹存在两个相邻问题：一是 Search 没有交付有用的后文；二是模型用未证实的推断补全了比赛关系。本轮只处理第一个问题，不预设片段改善后第二个问题就会消失。

### 2.2 qid 1094：命中正确比赛文档后，仍未检查具体事件

模型在第二次搜索中已经得到 23800《2005 UEFA Champions League final》。前 1600 字符主要包含比赛双方、比分和背景，具体比赛过程位于后文。

模型没有读取全文，而是在多个比赛假设间继续搜索，最终弃答。这个案例适合检查片段定位是否能把查询中的事件线索带入返回结果。

同时，离线核对发现，本地标注材料也没有完整保留题目中“第 95 分钟任意球”的精确原句。因此本轮不能将“命中标注文档”或“出现球员姓名”直接记为证据充分。

### 2.3 qid 517：保留成功案例，检查新方案是否丢失原有信息

原轨迹先从 67431 的开头发现 Peter King 的姓名和家庭背景，随后明确指出片段缺少具体影视角色，再调用 `get_document`，从后文表格确认 Policeman 1。最终答案实体正确。

```text
开头简介提供身份线索
          ↓
模型识别具体角色的信息缺口
          ↓
读取文档后文
          ↓
角色关系得到支持
```

如果新方案直接返回角色表格，却删除了促使模型识别候选的姓名和家庭信息，就可能破坏这条已有路径。因此，517 用于检查片段选择的收益与信息损失，不能只观察失败题是否获得更多后文。

## 3. 原因分析与改进思路

上述案例说明，Search 至少包含两个需要分别检查的环节：文档是否被召回，以及召回后实际展示了什么。

文档分数表示检索器对整条文档记录的相关性判断。固定截取开头则不考虑 query，也不检查关键关系的位置。即使第一阶段检索成功，模型仍可能只看到背景、导航或其他事件。

模型更换 query 后，如果命中相同文档，返回内容也不会变化。继续搜索不能自然扩展这篇文档的可见范围，必须依靠额外阅读。

因此，本轮在文档召回之后增加片段定位：

```text
现有文档检索
      ↓
召回文档全文
      ↓
切分原文片段
      ↓
按当前 query 排序
      ↓
在固定预算内返回片段
```

这个改动保留现有文档索引，也不增加模型必须执行的动作。它只改变 Search 的返回内容，使不同 query 有机会看到同一文档的不同位置。

其能力边界也很明确：第一阶段没有召回的文档，无法通过文档内定位补回来；如果 query 已经围绕错误候选展开，片段排序也可能继续偏向该候选。311、776 的召回问题暂不纳入本轮结论。

## 4. 实验一：相关片段定位 v001

### 4.1 实验问题与控制变量

本轮只回答一个问题：

> 对同一个 query 和相同的召回文档，按相关度选择原文片段，是否能比固定开头提供更有用的内容？

实验使用 64 轮批次中三题的全部搜索记录，共 27 次搜索、135 个文档返回条目，涉及 59 篇不同文档。query、文档集合、排名和文档分数都来自已保存轨迹，不重新执行第一阶段检索。

| 配置 | A：开头片段 | B：相关片段 |
| --- | --- | --- |
| Query | 原轨迹 query | 相同 |
| 文档集合与顺序 | 原轨迹 top-k | 相同 |
| 每篇文本上限 | 400 tokens | 400 tokens |
| 文本来源 | 文档开头 | 文档内最高分片段 |
| Tokenizer | 本地 Qwen3-Embedding-8B tokenizer | 相同 |
| 大模型调用 | 无 | 无 |
| 标准答案参与选择 | 无 | 无 |

400 tokens 是本轮用于控制比较范围的初始设置，尚未进行参数优化。两组采用相同上限，但不强制填满预算。B 可能为保留段落边界而返回更短文本，实际 token 数另行记录。

原在线版本使用 1600 字符，不能与 400 tokens 等同。因此 A 是本轮统一预算后的对照，不是原在线返回内容的完全复现。

### 4.2 分块方法

分块优先选择段落边界，其次选择换行；单行过长、无法在预算内完整容纳时，才按 token 范围切开。相邻片段仅在换行边界保留约最多 50 tokens 的重叠。

这个方法尽量保留完整段落和表格行，但尚未识别完整比赛记录，也没有为跨片段表格自动补回表头。原始文档不被改写。

每个片段保存原文起止位置、文本长度和稳定 chunk_id。ID 由文档身份、内容版本、分块配置及位置生成，使同一版本下的片段可以重复识别和复核。

### 4.3 排序与返回规则

每篇文档内部使用 BM25 对候选片段排序，取最高分片段。参数为 `k1=1.5`、`b=0.75`，相同 query 词项不重复累加，同分时选择靠前片段。

当前词项处理仅包含小写英文、数字和单个汉字，没有加入词干、同义词、短语、实体或日期约束。例如，Mark Selby 会被拆成独立词项；匹配 Mark 不代表匹配了这个人。

选择结果记录匹配词和分数，便于解释为什么选中某段。片段分数只在当前文档内用于排序，不与第一阶段文档分数混合。

没有词面匹配时回退到开头。原始 HTML 单独标记并回退到开头，本轮不增加正文清洗。这两种回退在本次对照中均未触发，不能据此认为 HTML 问题已经解决。

### 4.4 验证范围

实现验证覆盖了以下内容：

- 分块覆盖原文，片段位置、ID 和 token 上限符合约定；
- 简单查询能够选中后文，无匹配时执行回退；
- 能在预算内容纳的表格行不从行中间切断。

三项测试通过。135 个对照条目还逐项检查了片段与 SQLite 原文切片一致、A/B 不超预算，以及历史搜索视图与当前语料一致。

这些检查保证实现与原文记录一致，不代表片段在语义上完整，也不代表排序质量合格。

## 5. 效果对比

### 5.1 整体结果

| qid | 文档返回条目 | 选择非开头片段 | 所选片段起点超过历史可见范围 | A 文本 tokens | B 文本 tokens |
| --- | ---: | ---: | ---: | ---: | ---: |
| 546 | 50 | 28 | 25 | 19,402 | 16,818 |
| 1094 | 50 | 14 | 14 | 16,940 | 14,711 |
| 517 | 35 | 20 | 14 | 13,534 | 11,185 |

“历史可见范围”指原 Search 返回的前 1600 字符。表中统计的是文档返回条目，同一文档在不同搜索中出现会分别计数。

新方案确实改变了可见内容的位置，但这个变化不能直接换算为有效证据增加。表中的 token 为离线片段文本累计量，不是 API 用量，也没有包含工具 JSON 等外壳开销。

### 5.2 546：获得更具体的记录，但可能只匹配部分实体

第五次搜索的 query 为：

```text
"Mark Selby" 2023 Players Championship snooker results
```

对文档 55516，A 返回人物简介，B 从字符位置 34,885 选出 Selby 的 2023 年赛事经历。B 更接近当前要检查的年份和赛事问题，但其中仍没有确证 query 中假设的 Players Championship。

对文档 84585，B 从位置 52,080 选出 Mark Williams 对 Ding Junhui 的赛果。它恰好交付了与正确答案有关的线索，但排序匹配词只有 `mark` 和 `2023`，没有 `selby`。

因此，这个结果只能说明后文能够被选出来，不能说明排序正确理解了候选或题目关系。若直接将它计为成功，会把部分姓名重合带来的偶然结果当成算法能力。

此外，针对 Bingham 的第四次搜索中，所选片段包含前一场比赛的尾部和后一场比赛的内容。换行没有被切断，比赛关系却仍然不完整。这说明需要进一步检查语义记录的边界。

### 5.3 1094：事件词匹配，但时间条件不符

第二次搜索包含以下 query：

```text
Champions League final 95th minute free kick
```

B 在文档 23800 的位置 16,139 选出后文，匹配到 `free`、`kick` 和 `minute`。该段描述的是第 117 分钟及加时赛末尾的情节，与 query 中的第 95 分钟不符。

原文没有被改写，时间信息也仍然保留。问题发生在排序：词项得分较高，并不意味着所有关键条件都得到满足。

这份文档在其他多次搜索中又被选回开头，主要匹配赛事名称。只选择一个 BM25 最高分片段，尚不能稳定交付模型真正需要检查的事件。

### 5.4 517：角色表格提前可见，但身份信息被替换

第六次搜索的 query 为：

```text
actor played policeman in The Constant Gardener 2005
```

B 在 67431 中选择位置 1,426 开始的片段，其中包含 Policeman 1 和 2013 年影视角色表格。原轨迹需要调用 get_document 才能看到这些内容，新方案将其提前带入搜索返回。

但这个片段不包含开头的完整姓名和父母职业，返回结构也没有单独保留文档标题。模型可能更容易看到角色，却更难确认这些角色属于谁，以及为何符合题目其他条件。

这是一项明确的信息取舍。后续冻结 query 可能再次选回简介，但在线 Agent 在看到不同内容后，也可能发出完全不同的下一条 query。因此不能用冻结轨迹中的后续结果保证原成功路径不受影响。

## 6. 当前判断

本轮验证了一个有限但明确的结果：在不重建文档索引的情况下，文档内片段选择可以将部分后文带入 Search 返回。

同时，原型暴露出三个需要继续处理的问题：

| 问题 | 本轮依据 | 后续需要检查什么 |
| --- | --- | --- |
| 片段缺少身份上下文 | 517 返回角色表格，丢失姓名与家庭信息 | 标题、身份信息与正文片段如何共同占用固定预算 |
| 切分边界不等于关系边界 | 546 的片段跨越两场比赛 | 表头、双方名称、轮次、比分是否能组成完整记录 |
| 词项相关不等于条件满足 | Mark 的部分匹配、95 分钟与加时末尾的混淆 | 如何区分检索相关性与证据支持，是否需要改进排序 |

这些结果尚不足以支持直接替换在线 Search。当前没有新 rollout，也没有证明重复搜索减少、答案正确率提高或总成本下降。

## 7. 下一步安排

下一小步先处理片段的上下文完整性，继续保持第一阶段检索不变，并保留当前 BM25 排序作为对照。

首先检查文档标题和人物身份信息是否需要单独保留。如果增加这部分内容，要从相同的总 token 预算中分配，不能通过额外增加返回量掩盖效果来源。

其次检查比赛记录与表格结构。目标是让一个片段能够明确说明“谁与谁、在什么轮次、得到什么结果”，并避免上一场记录的尾部与下一场记录混在一起。

完成后，继续使用同一批冻结 query 和文档进行离线对照，检查相关内容的可见性与原有信息的保留情况。确认返回内容更完整后，再考虑接入在线 Agent。

BM25 对实体和时间条件的局限单独记录，暂不同时加入 embedding 排序、reranker、Research State 或 replan。后续若修改排序，应作为独立实验说明其新增作用。

## 9. v002：定位后扩展上下文

2026-09-18 完成第二轮离线实验。v001 的切分优先沿段落和换行结束，仍可能遗漏命中内容的相邻上下文。本轮将正文划为句子、表格划为行，用相同 BM25 公式选择定位单元，再交替向前后扩展，直至达到 400-token 上限或已识别的小节边界。

本轮继续使用相同的 27 次历史搜索、135 条返回项和 59 篇去重文档。A 复用 v001 固定块，B 使用定位后扩展；召回、原始 query 和文档顺序固定，没有新增在线 rollout。

| qid | 返回项 | 固定块文本 tokens | 扩展窗口文本 tokens |
| --- | ---: | ---: | ---: |
| 546 | 50 | 16,818 | 18,734 |
| 1094 | 50 | 14,711 | 15,901 |
| 517 | 35 | 11,185 | 13,136 |

135 条返回项中有 117 条窗口发生变化，实际文本 token 总量增加约 11.8%。相同上限不代表实际消耗相同，也不保证信息质量提高。

517 的角色表定位准确，扩展窗口保留了表头和相邻影视记录，但仍未覆盖文首身份。1094 出现明确退化：定位单元变为文末 `UEFA Champions League Final` 分类词，窗口主要返回流行文化和分类内容，偏离比赛过程。546 的普通文本赛季标题未被识别，扩展窗口仍跨越赛季边界。

这些现象说明，定位后扩展需要分别检查定位质量与上下文边界。虽然 BM25 公式没有变化，句子/行替代固定块会改变统计量及排序，因而本轮不能单独归因于扩展操作。当前实现仅识别 Markdown 标题，不理解所有普通标题、赛事记录或表格关系。

本版本暂不接入在线 Search。下一步优先固定定位单元，单独检查扩展增加了什么信息；随后再处理短分类词导致的定位偏差，以及标题和身份信息的保留。5 项相关测试通过，验证原文、预算和边界规则，不代表搜索效果或答案正确率改善。

完整方案、结果与原文实例见 [v002 实验报告](../experiments/offline/snippets_v002/20260917T172302.738631Z/README.md)，实现见 [window.py](../experiments/snippets/window.py)，运行入口见 [compare_windows.py](../experiments/snippets/compare_windows.py)。

## 10. v003：当前 query 下的单块与多块

本轮明确限定评价范围：Search 只负责当前 query 的信息需求，原题的约束拆分和 gap 留给后续模块。517 缺少家庭背景不计为搜索缺陷；角色表无法明确归属到人物，仍属于当前需求的上下文问题。历史 query 保持原样，未重新构造单约束题集。

实验固定 v001 的分块和 BM25 排序，比较一个块与最多两个不重叠块，每块最多 400 tokens。全部 top-1 ID 与分数一致，从而避免 v002 中定位粒度变化带来的混淆。本轮先增加总预算，尚未比较相同总预算。

135 条返回项中有 105 条增加第二块，文本总量从 42,714 增至 78,133 tokens，增加约 82.9%。240 个输出片段均通过实际 get_document 按位置读取并校验原文。这只验证 Search 到 Open 的位置衔接，没有验证模型阅读行为。

1094 的第二块补充赛事年份和球队，能帮助识别 2008 年 query 与 2005 年文档的不匹配；546 的人物文档第二块主要为分类词，没有补充所需赛事结果。517 的人物身份块因与角色块共享一个换行字符而被排除，说明严格的字符不重叠规则会误删有用信息。

多块返回具有补充当前需求上下文的潜力，但尚无整体效果或成本收益结论。下一步优先单独验证纯空白重叠的处理，再开展等总预算对照。人工案例审查未覆盖全部返回项，不据此计算语义有效率。新增两项测试通过，在线 Search 未替换。

完整配置、统计和原文见 [v003 实验报告](../experiments/offline/snippets_v003/20260917T173025.031319Z/README.md)。

## 11. v004：修正空白重叠并比较相同总预算上限

本轮先允许只有空白字符的块间交集，仍排除包含正文的交集；然后固定选中块，将双块文本上限设为总计 400 tokens。默认各分 200，短块剩余额度转给另一块，按前缀截取。保留旧严格规则和 800-token 双块组，分别观察规则修正与预算收缩的影响。

135 条返回中，空白修正改变了 14 条的选择，其中 5 条新增第二块，双块数从 105 增至 110。单块组实际文本量为 42,714 tokens，等上限双块组为 49,249 tokens。两者上限相同，但实际消耗不完全一致，后者增加约 15.3%；元信息未计入。

517 的角色块和身份块不再因一个换行重叠而互斥。两块各 200 tokens 时，仍能同时展示人物姓名与 Policeman 1 记录，满足当前 query 的信息理解需要。1094 的短块保留 122 tokens，第二块获得 278-token 额度，仍能显示与 query 年份不符的赛事身份。

546 暴露另一项限制：分类词占用第二块额度，正文被缩短；比赛统计或选手标签也可能被前缀截取切断。因此可以保留空白重叠修正，但尚不能据此将等分预算双块替换在线 Search。

458 个原文范围通过现有 get_document 回读校验，4 项相关测试通过。没有新增在线 rollout。下一步可固定候选与预算，单独检验短窗口构造；第二块是否值得占用预算另行分析。人工复核四个特定条目，不外推整体语义有效率。

完整配置和原文见 [v004 实验报告](../experiments/offline/snippets_v004/20260917T173648.577447Z/README.md)。

## 12. v005：固定父块和额度的短窗口构造

本轮固定 v004 的父块、顺序与每块额度，仅调整需要缩短的块内窗口。原方案从块首截取；新方案在父块内按句子或行定位 query，再扩展相邻单元。能够直接放入额度的块保持不变。父块选择和总预算没有改变，但块内定位会改变模型可见信息。

135 条返回包含 245 个块，203 个块内容改变。实际文本量从 49,249 降至 46,079 tokens，减少约 6.4%，原因是完整单元放不下时停止扩展。245 个新窗口通过现有 get_document 回读校验，4 项相关测试通过。存在 1 个超长单元切分的定位点，未保证所有语义边界完整。

1094 的赛事身份信息保留，窗口不再附带截断的正文半句。546 的部分句子和选手标签得到改善，但统计行仍可能跨比赛，分类噪声也没有消失。

517 暴露关键退化：角色块更集中于电影表格，第二块却因电影词匹配移动到职业经历，丢失原先保留的人物姓名。这影响当前 query 所问角色的归属，不属于题目其他约束。单独提高每个窗口的 query 相关性，可能损害多窗口之间的信息互补。

本版本继续作为离线候选，不替换 v004 或在线工具。下一步应先固定原前缀位置，仅检查沿完整边界收缩的作用，将窗口位置变化与边界改善分开。四个实例的人工复核不外推整体语义效果。

完整结果见 [v005 实验报告](../experiments/offline/snippets_v005/20260917T174229.428315Z/README.md)。

## 13. 统一 Search/Open 最小闭环实现

本轮将前述设计接入默认 Agent。Search 保留 Qwen3-Embedding-8B 文档召回，使用文内 BM25 定位后，从完整文档构造单个原文窗口。标题独立提取并计入每篇 400-token 总展示上限；窗口不受原定位块边界限制。

Open 接受窗口引用和 before、after、around。before/after 分别读取前后相邻范围，不重新排序；around 保留原范围并扩展。旧窗口是不可变观察，标识包含文档版本与原文位置。当前未加入 focus、gap、强制阅读或研究阶段控制。

四篇真实文档完成固定 query 的工具检查，Search 与三个 Open 方向均通过原文一致性断言，连续 after 可读取到文档末尾。517 对应文档同时返回人物标题与角色记录。该结果验证工具协议，不代表模型已改善阅读决策或最终答案。

当前弱结构规则仍不能保证表头、普通章节和比赛记录完整；进程内窗口缓存尚无淘汰机制。新增运行使用 v001_raw_windows 目录，与历史 v000 分开。完整协议见 [RAW_WINDOWS.md](../llm_chat/RAW_WINDOWS.md)，真实原文检查见 [检查报告](../experiments/offline/raw_windows_v001/20260917T180933.868485Z/README.md)。

## 14. 首轮在线深测：工具闭环可运行，阅读行为仍需验证

使用统一 Search/Open 对 517、546、1094 运行独立轨迹，预算均为 64 轮。517 进行了 5 次 Search，人物回答正确但具体角色及部分解释未获充分验证；546 进行了 3 次 Search，错答 Judd Trump；1094 进行了 7 次 Search、1 次 Open，最终未确认答案。

三题均自然停止，合计 226,386 API tokens。历史对应三题为 521,273 tokens，但独立采样轨迹的 query 和停止时机不同。546 提前错答尤其说明，不能将调用减少直接计为效率改善。

517 的实际 query 与离线实验不同，两次返回人物简介，未显示后方角色表。546 的 Search 已返回 Ding Junhui 文档，但定位窗口和模型候选判断没有形成完整核查。1094 唯一一次 Open 打开了 Search 已全文返回的短页面，新增原文为零。窗口引用、预算和工具执行没有异常，不代表模型已经有效阅读。

## 15. 固定真实 query 的 Search–Open 局部诊断

本轮将评价限定在工具节点，冻结上轮 15 次 Search 的 75 条返回、53 篇去重文档，不重新召回或调用模型。全部 Search 精确复现，225 次 before/after/around 离线探测均与原文一致。

517 的角色 query 在人物简介块上获得 BM25 5.872428，高于角色表块的 4.927818；局部锚点再选中人物简介，400-token 窗口无法到达角色表。一次 after 或 around 即可返回所需角色记录。因此需要区分 Search 定位不足与 Open 能力是否可用。

546 的比分被拆为 4、3、0 等独立词项，统计表的数字匹配可能获得高分；另一文档的优胜块只匹配 decider、centuries 等词，没有命中 2023。此处仅诊断文内排序，不涉及候选纠偏或最终答案。

17 条返回已覆盖全文，around 却标记预算内无法展开。已单独修正为 document_complete，保留原引用与文本；尚有内容但无法在预算内展开时继续使用原状态。8 项相关测试通过。排名与窗口算法未在本轮修改。

下一步将角色词定位与比分分词分别做固定输入对照，不引入 gap、强制阅读或长链路指标。完整候选、原文和状态修正快照见 [局部诊断报告](../experiments/offline/search_open_diagnosis/20260917T182655.718687Z/README.md)。

## 16. 文内定位消融：扩大候选与保留比分表达

继续固定 75 个真实 query–文档对，分别测试前三个父块合并锚点候选，以及数字对正规化。两组不合并，标题、窗口构造和 400-token 总上限保持不变。

扩大候选改变 16 个窗口。517 的第五次查询能够选中角色表，说明原先第一父块的限制确实影响定位。但其他文档出现 next: 2023 等元信息成为锚点，暴露正文与结构字段混合竞争的问题。

比分词法改变 8 个窗口。4975 窗口开始包含完整的 4–0 与 4–3，但分别属于 2010 和 2013 年；38231 仍定位旧赛季。数字表达保留只能改善词法，不能自动建立年份与同一比赛记录的关系。该原型也会处理数字区间，不能视为成熟比分解析器。

全部输出通过原文及预算断言，两项词法测试通过。当前保持线上排序不变。下一步优先固定候选范围，单独检验元信息能否作为独立锚点，再用未参与设计的数据复核；不引入年份硬过滤或候选语义控制。

## 17. 阶段验收：为后续提供适量信息，不承担 gap 求解

本轮重新明确节点目标：Search–Open 提供相关、可理解、可继续读取的原文；不要求解决所有缺失信息、完成 BC+ 原题或控制研究阶段。冻结当前实现，准备 20 个局部需求，在固定文档条件下对比旧前缀＋分页与当前窗口＋Open。

正式测试包括 40 次模型阅读会话，允许最多两次继续读取。19 个正向需求首次显示指定参考原文的数量从 13 增至 16，其中 8 个未用于窗口调优的新需求从 6 增至 8。实际读取调用从 3 次降至 1 次，工具错误为零。参考片段可见性不是语义支持率；有一例新窗口提供同一事实的另一处原文，未被该指标计入。

首次序列化观察量由 9,505 增至 12,015 本地 tokens，计入继续读取后由 14,422 降至 13,098。两组不是等预算实验，API 用量差异也包含模型输出与采样差异，不能直接外推成本收益。

具体收益包括后文任意球描述、角色正式姓名、扑克决赛对手更早可见。局部限制仍包括人物别名与标题不一致、角色表未进入初始窗口，以及模型将占位页标题或页面日期过度解释。这些作为接口回归项保留，不将解决 gap 强加给当前节点。

第一次协议试运行把初始 Search 放入历史却只开放阅读，出现无效搜索请求；明确固定文档范围后重新成对运行，正式结果不与试运行混算。当前实现可以作为后续研究的信息接口基线，但小规模手选样本不足以证明稳定泛化。

完整样本、请求、返回、人工复核和统计见 [局部信息支撑测试](../experiments/local_support/runs/20260917T184725.353925Z/README.md)。

## 18. 机械修复：结构边界、Open 与性能

本轮保持文内排序和语义职责不变。修复空 title 字段跨行吞入正文；保留原锚点后，尝试按全文句子/行边界补齐范围；对明确的 Markdown 管道表格，在连续范围可放入预算时带回表头。这些操作只处理原文结构，不解释主体或记录含义。

同时预存边界数组，增加每实例最多 256 项的 token 计数缓存。33 项全量测试通过，覆盖连续翻页、around 饱和、原文和引用一致性、Unicode、长文本及新增边界处理。

四篇真实文档的新旧 Search 范围一致。相同请求重复时计数缓存明显降低延迟，但约 115 万字符 HTML 首次处理仍需约 6 秒，未出现稳定冷启动加速。文档注册表仍持续保留，缓存淘汰与长期引用恢复没有在本轮仓促实现。

新运行目录版本为 v002_raw_windows_mechanical，历史实现与测试日志独立保存。未调用模型 API，未改变模型字段组织。完整前后数值与限制见 [机械修复报告](../experiments/mechanical/runs/20260917T190036.604272Z/README.md)。
